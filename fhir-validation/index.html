9.3

fhir-validation: checking FHIR resources🔗

Health data is exchanged as FHIR resources: a patient, a lab result, a prescription, each a small JSON document. FHIR says exactly what each kind may contain, and a receiving system will refuse one that breaks the rules: a misspelt field, a date that is not a date, a code that is not among the allowed ones, a required field left out.

This package is the validator. You give it a resource, and it lists what is wrong and where. You can also give it stricter rules of your own or of a published guide, and it holds the resource to those too. The command is raco fhir-validate.

Part of the fhir family of FHIR languages and tools.

1 What you can do with it🔗

  • Check one resource against FHIR’s own rules: A first example.

  • Hold it to a profile, a stricter set of rules for one setting ("every patient has an identifier"): Checking against a profile.

  • Hold it to a published Implementation Guide such as US Core: Checking against an Implementation Guide.

  • Decide how far to trust the answer: an error is always real; a clean answer covers what could be checked (What it does not decide, and what that means for trust).

  • Validate from a program, or stop a pipeline at the first invalid resource: From a program.

2 A first example🔗

1. Install the tools as the family’s front page describes. The command is then raco fhir-validate (or fhir-validate, if you built the standalone tools).

2. Have a resource. Here it is a patient, in patient.json:

{"resourceType": "Patient", "id": "ann",

"name": [{"family": "Lee", "given": ["Ann"]}],

"gender": "female", "birthDate": "1974-12-25"}

3. Check it.

$ raco fhir-validate patient.json --format text

patient.json: information informational: All OK

Nothing was found. --format text asks for one line per finding, for a person to read; without it the same answer comes as a FHIR OperationOutcome, the JSON document FHIR uses to report problems, for a program to read (Running it).

4. Make two mistakes. Write the gender in French and give February thirty days (bad.json):

{"resourceType": "Patient", "id": "ann",

"name": [{"family": "Lee", "given": ["Ann"]}],

"gender": "femme", "birthDate": "1974-02-30"}

$ raco fhir-validate bad.json --format text

bad.json: error code-invalid at Patient.gender: code `femme` not in required value set http://hl7.org/fhir/ValueSet/administrative-gender; it holds female, male, other, unknown

bad.json: error invalid at Patient.birthDate: '1974-02-30' is not a valid date (February 1974 has 28 days)

Both are found in one run, each with the place and the reason. The command exits with 1 because there is an error, so a script can stop on it.

3 Reading an issue🔗

Every finding is called an issue, and every issue line has the same five parts. Take the first line above:

part

  

here

  

what it is

file

  

bad.json

  

the file that was checked

severity

  

error

  

how serious: error, warning or information (Errors and warnings)

kind

  

code-invalid

  

the kind of rule that was broken, from FHIR's own list (below)

place

  

at Patient.gender

  

the element, as a path from the top of the resource

message

  

code `femme` not in …

  

what was found, the rule, and often what to write instead

The place is a dotted path: Patient.contact is the contact element of the patient, Observation.component.value[x].code the code of the value of a component (value[x] is how FHIR writes "the value, whichever type it has": valueQuantity, valueString …). A problem inside a nested part may be named from that part: Narrative.div for the text of any resource, Observation.status for an Observation contained in a Patient.

The kinds you will meet:

kind

  

meaning

  

example message

structure

  

an element FHIR does not define there, or an unknown resource type

  

element 'birthdate' is not defined at Patient (did you mean `birthDate`?)

required

  

too few or too many of an element

  

minimum required = 1, but found 0

invalid

  

a value in the wrong form: a date, a number, an id; a JSON key written twice

  

'1974-02-30' is not a valid date (February 1974 has 28 days)

value

  

a value other than the one a profile fixes

  

value does not match fixed value true

code-invalid

  

a code outside the set of codes allowed there; a unit that is not a UCUM unit

  

code `femme` not in required value set …

invariant

  

a rule that relates several elements

  

pat-1: SHALL at least contain a contact's details or a reference to an organization (found no name; no telecom; no address; no organization)

An invariant is a rule FHIR or a profile writes as a formula over the resource, with a short key (pat-1) and a sentence for people. When one is broken, the message gives the key, the sentence, and in parentheses what the validator found in the elements the rule looks at, so you can see which part failed:

obs.json: error invariant at Observation: obs-6: dataAbsentReason SHALL only be present if Observation.value[x] is not present (found dataAbsentReason = not measured; value = 72 '/min')

4 Errors and warnings🔗

An error means the resource breaks a rule: it is not valid. A warning means something is probably wrong, but the resource is still valid. An information line is only the "All OK" you get when nothing was found.

Here is a blood-pressure reading whose unit is written the common way, mmHg. FHIR quantities name their units in UCUM, the standard for unit codes, and UCUM writes millimetres of mercury as mm[Hg]:

$ raco fhir-validate bp.json --fhir-version 4.0.1 --format text

bp.json: warning code-invalid at Observation.component.value[x].code: `mmHg` is not a UCUM unit (mercury is written mm[Hg])

It is a warning, not an error, because published examples from HL7 itself contain such units; a system that computes with the value will still stumble on it, so fix it. Warnings come from two places: a unit that is not a UCUM unit, and an invariant that its author marked as a warning.

The exit code follows errors only: 0 when there is none (warnings or not), 1 when there is at least one, 2 when the command was called wrongly.

5 What "valid" means🔗

A resource is valid when it follows two sets of rules.

FHIR’s own rules for its type. Every Patient, whoever sends it, must be a Patient as FHIR defines one. The validator checks:

  • that resourceType names a real type (`Observaton` is not a resource type (did you mean `Observation`?));

  • that every element is one the type has, spelt and capitalised as FHIR does;

  • how many of each element there are: a required one is present, a single one is not a list;

  • that each value has the form of its type: a date is a real calendar date, a decimal a number and not a string, an id only the characters an id may have;

  • that a value written under a choice (valueQuantity, valueString …) is of a type the element allows;

  • that a code is in the value set where FHIR requires one (a required binding: gender must be female, male, other or unknown);

  • the type’s invariants, and that a contained resource is referred to from the resource that holds it (or refers to it);

  • a few rules about a whole resource: a value set’s compose names each code system by an absolute URI (a contained one by its url, with the valueset-system extension), and a Questionnaire derived from another (derivedFrom, with the derivation type extends or compliesWith) keeps what the other says of each item they share — its type, that it does not repeat, that it is required, its answer options — and, when it complies, adds no item;

  • that the JSON itself is sound: no key written twice, nothing malformed.

The rules of each profile it is held to. A profile narrows a type for one setting: it makes optional elements required, fixes values, restricts codes, adds invariants. A resource is held to a profile in two ways: it claims the profile by listing the profile’s address in its meta.profile, or you name the profile when you validate. Either way the checks are the same as above, with the profile’s stricter answers, plus:

  • values a profile fixes or gives a pattern for;

  • slices: a profile can say that a repeating element must contain particular entries, told apart by a value. A blood pressure must have one component coded systolic and one coded diastolic; an entry that matches a slice is held to that slice’s own rules.

6 Checking against a profile🔗

A profile is itself a FHIR resource, a StructureDefinition, so on the command line it is a JSON file. Give it after the resource. This is the US Core Patient profile, which requires an identifier, and the patient from the first example has none:

$ raco fhir-validate patient.json StructureDefinition-us-core-patient.json --fhir-version 4.0.1 --format text

patient.json: error required at Patient.identifier: minimum required = 1, but found 0

You can give several profiles. One written for another type than the resource’s is passed over without a message: a Patient profile says nothing about an Observation.

A profile checks more than counts. The blood-pressure reading above has only its systolic component, and the US Core blood-pressure profile wants two components, one of them the diastolic:

$ raco fhir-validate bp.json StructureDefinition-us-core-blood-pressure.json --fhir-version 4.0.1 --format text

bp.json: warning code-invalid at Observation.component.value[x].code: `mmHg` is not a UCUM unit (mercury is written mm[Hg])

bp.json: error required at Observation.component: minimum required = 2, but found 1

bp.json: error required at Observation.component: slice 'diastolic' requires 1, found 0

FHIR versions. FHIR has several versions in use, and a resource valid in one may not be in another. The command checks against R5 unless you say otherwise with --fhir-version 4.0.1 (R4), 5.0.0 (R5) or 6.0.0 (R6), or unless the resource states its own version in a fhirVersion element, as a CapabilityStatement or a StructureDefinition does, or you name a guide’s package (Checking against an Implementation Guide), which brings its own version. US Core is written for R4, hence the option above.

If you write your profiles in FHIR Shorthand you do not need this command at all: raco fsh check validates every example in a project against the project’s profiles with this validator, and points at the line of the FHIR Shorthand that wrote the offending value.

7 Checking against an Implementation Guide🔗

An Implementation Guide (IG) is a published set of profiles, value sets and examples for one purpose: US Core for exchanging records in the United States, the International Patient Summary, mCODE for cancer data. It is distributed as a package, one .tgz file. There are three ways to hold a resource to one.

On the command line, with the package. Name the guide’s package with --package. The command reads it with the packages it depends on, finds in them every profile the resource claims, and validates in the FHIR version the guide is written for:

$ raco fhir-validate claims.json --package hl7.fhir.us.core-6.1.0 --format text

claims.json: error required at Patient.identifier: minimum required = 1, but found 0

claims.json is a patient that lists the US Core patient profile in its meta.profile and has no identifier (it is shown in What it does not decide, and what that means for trust). A package is named as it is installed (hl7.fhir.us.core-6.1.0) or by its file (./my-guide.tgz); repeat the option for more than one. To hold a resource to one profile it does not claim, give that profile’s file instead, as in the section above: a package is an archive of JSON files, one per profile, so tar -xzf hl7.fhir.us.core-6.1.0.tgz package/StructureDefinition-us-core-patient.json takes one out.

From a program, with the whole package. There the validator takes a list of packages, and finds in them every profile a resource claims, the profiles those build on, and the value sets they use (From a program).

Through a server made from the guide. raco fhir-server serve-ig starts a FHIR server from an IG’s package. It validates every resource written to it against the guide, refuses the invalid ones with the same issues, and answers $validate requests.

The packages that come with the tools (in the fhir-spec package) are the core specification for R4, R5 and R6, US Core 6.1.0, 8.0.0 and 9.0.0, the International Patient Summary 2.0.1, mCODE 4.0.0, CQF Measures 5.0.0, CRMI 2.0.0 and Genomics Reporting 2.0.0. Any other package is a file you download from packages.fhir.org.

8 What it does not decide, and what that means for trust🔗

The validator has one rule above the others: it never reports what it cannot decide. If it cannot find a profile, cannot work out which codes a value set holds, or cannot evaluate an invariant, it says nothing about that point rather than guess. (This is sometimes called failing open.)

That makes its two answers worth different things.

  • An error is real. Each one states a fact about the resource and a rule the validator could read in full. It is held to this by the examples that guides publish: every example in US Core, the International Patient Summary and CRMI validates against its own profiles with no error (How it is tested). You can act on an error without second-guessing it.

  • "All OK" means nothing was found in what could be checked. It is not a certificate. A different validator, or this one with more to go on, may still find something.

One such case is said out loud, because it is the easiest to misread: a profile the resource claims that the validator could not find. This patient claims the US Core profile, and has no identifier:

{"resourceType": "Patient", "id": "ann",

"meta": {"profile": ["http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient"]},

"name": [{"family": "Lee", "given": ["Ann"]}],

"gender": "female", "birthDate": "1974-12-25"}

$ raco fhir-validate claims.json --fhir-version 4.0.1 --format text

claims.json: warning not-found at Patient.meta.profile[0]: the resource claims profile

  `http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient`, but nothing in context

  defines it: it was not checked against that profile

$ raco fhir-validate claims.json --package hl7.fhir.us.core-6.1.0 --format text

claims.json: error required at Patient.identifier: minimum required = 1, but found 0

(The warning is one line; it is wrapped here to fit the page.) The first run had only FHIR’s own rules, by which the patient is fine, so there is no error and the command exits 0. But it could not see the profile, and it says so. The second run was given the guide’s package. So when a clean answer matters, make sure the validator had the profiles and packages the resource depends on, and read the warnings.

One thing is decided rather than passed over: a name that is simply wrong. A misspelt resource type or element is reported, with the nearest real name, because the packages at hand define all the names there are.

What is never checked, whatever you give it, is listed in Limits.

9 Running it🔗

9.1 Command line🔗

raco fhir-validate r.json

  

check against FHIR's rules for its type; the answer is an OperationOutcome

raco fhir-validate r.json --format text

  

one line per issue, for reading

raco fhir-validate r.json p1.json p2.json

  

also against these profiles (StructureDefinition files)

raco fhir-validate r.json --package hl7.fhir.us.core-6.1.0

  

with a guide’s package (a name, or a .tgz file) and what it depends on in reach, so the profiles the resource claims are found; repeatable

raco fhir-validate r.json --fhir-version 4.0.1

  

as FHIR R4; 5.0.0 and 6.0.0 likewise. Without it: the version the resource names, else the first package’s, else R5

raco fhir-validate --help

  

the usage line

--format chooses the form of the answer. outcome, the default, prints the OperationOutcome as JSON on standard output:

$ raco fhir-validate bad.json

{"issue":[{"code":"code-invalid","diagnostics":"code `femme` not in required value set …","expression":["Patient.gender"],"severity":"error"},{"code":"invalid","diagnostics":"'1974-02-30' is not a valid date (February 1974 has 28 days)","expression":["Patient.birthDate"],"severity":"error"}],"resourceType":"OperationOutcome"}

text prints one line per issue on standard error. json prints the OperationOutcome too.

A file that is not JSON at all is reported where reading stopped, and a key written twice in one object (which most JSON readers silently accept, keeping the last) is an error:

$ raco fhir-validate mal.json --format text

mal.json:1:48: json parse error: expected , or } in object

 1 | {"resourceType": "Patient", "gender": "female" "x": 1}

   |                                                ^

$ raco fhir-validate dup.json --format text

dup.json: error invalid at gender: duplicate JSON property 'gender'

A file that does not exist, or an option the command does not have, is said in one line, with exit code 2.

9.2 From a program🔗

In FHIR, validation is an operation called $validate. Here an operation is an ordinary function, so a Racket program validates by calling it. The resource is FHIR JSON as read-json gives it; the answer is an OperationOutcome, also JSON.

(require json fhir/operation fhir/sd/sd-index fhir/spec-package
         fhir/conformance/operations fhir/r4/schemas)
(define patient (call-with-input-file "claims.json" read-json))
(define us-core (spec-package-path "hl7.fhir.us.core-6.1.0.tgz"))
(define r4-core (spec-package-path "hl7.fhir.r4.core.tgz"))
 
(parameterize ([current-sd-packages (list us-core r4-core)])
  (apply-operation "$validate" patient))
; => an OperationOutcome with one issue:
;  error Patient.identifier: minimum required = 1, but found 0

current-sd-packages is the list of packages to look things up in: the guide first, then the core package it is written for. With US Core in the list, the profile the patient claims is found and applied, which the command line could not do. spec-package-path finds a package that comes with the tools by its file name; a package you downloaded is just its path.

To hold a resource to a profile it does not claim, name the profile by its address:

(apply-operation "$validate" patient
                 #:profile "http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient")

A clean answer is one information issue that says which FHIR version the resource was held to: All OK (FHIR R4 (4.0.1)).

Stopping a pipeline. ensure-valid returns the resource when it is valid and raises an error otherwise, so it can sit between two steps of a program:

(ensure-valid patient #:profile "http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient")
; raises exn:fail:operation:
; invalid Patient against http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient (FHIR R4 (4.0.1)):
;  Patient.identifier minimum required = 1, but found 0

The message lists every error and names the profiles and the FHIR version; the exception carries the OperationOutcome. In a threaded pipeline it reads (~> qr (transform #:srcMap fml) (ensure-valid #:profile url)).

Where profiles are looked for. A profile named by #:profile or claimed in meta.profile is looked for, in this order: among the resources of current-data-source (StructureDefinitions you hold as data); among the definitions that Racket modules written in the family’s languages have registered (a #lang fsh file’s profiles, once the file is required); in the packages of current-sd-packages. With no packages set, the R5 core package is used.

; an FSH project's profiles, compiled by fsh/project
(parameterize ([current-data-source (resources->data-source (project-artifacts ig))]
               [current-sd-packages (project-sd-packages ig)])
  (ensure-valid observation #:profile url))

9.3 The validator itself🔗

Under the operation is one function, validate-issues. It takes the resource and the profiles as StructureDefinitions already in hand, and returns the issues as values rather than as an OperationOutcome:

(require fhir/conformance/validate fhir/terminology/service fhir/r4/schemas)
(parameterize ([current-sd-packages (list us-core r4-core)])
  (validate-issues bp #:profiles (list blood-pressure-profile)
                   #:terminology (make-terminology/packages (list us-core r4-core))))
; => (list (issue "warning" "code-invalid" "Observation.component.value[x].code" "`mmHg` is not a UCUM unit …")
;  (issue "error" "required" "Observation.component" "minimum required = 2, but found 1")
;  (issue "error" "required" "Observation.component" "slice 'diastolic' requires 1, found 0"))

9.4 Which codes can be checked🔗

Whether a code is allowed is a question about a value set, and answering it needs the list of codes the value set holds. The validator knows that list in two ways.

  • For the value sets FHIR itself binds as required and that list their codes (gender, an Observation’s status and the like), the lists are built into the tools. The command line uses these, and only these.

  • For anything else it asks a terminology service, given as #:terminology: a value set from a guide, or one defined by a rule ("every code below this one") rather than a list. $validate builds a service over the data source and the packages by itself.

When neither can list the value set, for instance one drawn from SNOMED CT, which is not shipped, the code is not checked. The service and what it can answer are described with fhir-tx.

10 Where else it runs🔗

You will often meet this validator through another tool rather than by its own command.

  • FHIR Shorthand. raco fsh check validates a project’s examples against its profiles and reports each issue at the line that wrote the value.

  • Servers. A fhir-server validates every resource before it stores it and answers 422 with the issues when it is invalid; it serves $validate over HTTP.

  • The mapping language. fml can validate what a map produced and name the rule of the map that wrote the bad value.

  • An AI agent’s workspace. In fhir-mcp, data is validated when it is staged, and a change with an error cannot be committed.

11 Limits🔗

What the validator does not check. None of these produces a message: a resource that is wrong only in these ways gets "All OK".

  • References. A reference to another resource ("reference": "Patient/ann") is not followed: not whether the target exists, not whether it is of an allowed type or profile, not a #id pointing into contained.

  • Extensions. An extension is checked for its shape: its elements, the type of its value, and that it holds a value or nested extensions and not both. When the packages in context hold the definition its url names, it is held to that definition’s types, nested extensions and required codes. Where an extension may be used (its context), and the invariants of its own definition, are not checked. For an extension whose definition is the copy inside a FHIR core package, required codes are not checked: those value sets have grown since the release.

  • Codes where the binding is not required. Only required bindings are checked. Extensible and preferred bindings, a maximum value set and additional bindings are not. One thing is checked whatever the binding: a code of a code system that the packages in context hold whole must be one of that system’s codes. A code of a system that is not there (SNOMED CT, LOINC) is not checked at all.

  • Some slicing. Slices told apart by a value, a pattern or the value set their codes must come from are checked, for the fewest and the most entries a slice may have. Slices told apart by whether an element exists, by type, by profile or by position are not, and neither is a rule that a list may hold nothing but its slices (closed slicing).

  • Profiles inside a resource. A contained resource, or an entry of a Bundle, is held to FHIR’s rules for its type but not to the profiles its own meta.profile claims.

  • The narrative. A resource’s human-readable text (text.div) must not be empty; that it is well-formed XHTML is not checked.

  • Some invariants. The rules every element and every resource carries (ele-1, the dom- rules) are skipped, as is an invariant defined on a slice. (ext-1, an extension has a value or extensions, and dom-3, a contained resource is referred to, are checked on the JSON; the invariants of datatypes, such as "a contact point with a value has a system", are evaluated at every value of the type.) An invariant that depends on following a reference (resolve()) finds nothing to follow, and one whose formula cannot be evaluated counts as held.

  • Must-support. A profile’s "must support" flags are obligations on systems, not on a single resource, and are not checked, by design.

  • A claimed profile that is not at hand. The resource is checked without it, and a warning says so (What it does not decide, and what that means for trust). Give the guide’s package with --package.

  • No terminology service on the command line. raco fhir-validate checks codes against the value sets in the core package and in the packages you name. It has no option to ask a terminology server about SNOMED CT or LOINC codes.

  • JSON only. FHIR written as XML is not read.

12 Words used here🔗

  • Resource: one FHIR document, such as a Patient or an Observation, written as JSON.

  • Element: one named part of a resource (birthDate, component.code).

  • Profile: a set of stricter rules for one type of resource in one setting. As a resource it is a StructureDefinition.

  • meta.profile: where a resource lists the profiles it claims to follow.

  • Implementation Guide (IG): a published set of profiles, value sets and examples. Package: the .tgz file it is distributed as. The core package is the FHIR specification itself in that form.

  • Canonical url: the web address that names a profile or a value set. It is a name; nothing needs to be served there.

  • Cardinality: how many of an element are allowed, written min..max (1..1, 0..*).

  • Value set: a named set of codes. Binding: the statement that an element’s code comes from a value set; a required binding allows no other code.

  • Invariant (or constraint): a rule relating several elements, written as a FHIRPath formula, with a key such as obs-6.

  • Slice: one named entry a profile requires in a repeating element, such as the systolic component of a blood pressure.

  • Choice element: an element that may hold one of several types, written value[x] in a path and valueQuantity, valueString … in the JSON.

  • Issue: one finding. OperationOutcome: the FHIR resource that carries a list of issues.

  • Operation: a named service FHIR defines, written with a dollar sign ($validate).

  • Terminology service: the part that knows which codes a value set holds (fhir-tx).

  • UCUM: the standard codes for units of measure (mm[Hg], mg/dL).

  • Fail open: to say nothing where a rule cannot be decided, rather than report a possible problem.

13 How it is tested🔗

Against published work, in two directions: it must not complain about what is valid, and it should catch what is not.

  • No false alarm on published guides. Every example in US Core 9.0.0, the International Patient Summary 2.0.1 and CRMI 2.0.0 that claims one of the guide’s profiles is validated against it: 330 examples (216, 44 and 70), none with an error. mCODE 4.0.0’s 283 examples are held to its profiles the same way, through a server generated from the guide.

  • No false alarm on the specification. Of the 2,968 resources in the R5 core package, 2,957 show no broken invariant; the other 11 are real faults in the package (ten logical models without a derivation, and one code system against a profile it claims).

  • Against HL7’s validator test cases. On 67 cases with the reference validator’s recorded verdicts, it never calls a valid case invalid, and catches 22 of the 26 invalid ones. Of the four it misses, two are a CareTeam invariant that holds as FHIRPath defines is on nothing (the reference reads it otherwise), and two rest on content that is not here: LOINC’s codes, and an extension definition the reference could not find.

  • Against HL7’s validator, resource by resource. HL7’s validator judged 741 resources: the 28 published examples of six US Core profiles, and 713 copies of them with one change each (an element removed, a code replaced, a list entry doubled, a value that is no value, an element the type does not have). This validator gives the same verdict on 740. It refuses none that HL7’s passes; it passes one that HL7’s refuses (an NPI identifier with no value: the NPI rule comes out empty there, which this validator counts as held). On the next six US Core profiles (3,145 cases, none read when the validator was changed) the verdict was the same on 3,111; reading the five it refused and HL7’s passes found one cause (a best practice rule reported as an error), and after it the same on 3,116, refusing none HL7’s passes; reading the 29 it passed and HL7’s refuses found three places it did not look (a constraint on a choice element, nested Questionnaire items, a primitive’s extensions), and after them the same on all 3,145.

Validates raw FHIR JSON against its base type, the profiles in meta.profile, and the StructureDefinitions given (those whose type matches), their snapshots generated on demand. The checks: cardinality; unknown elements (lenient on choice variants) and unknown resource types; the choice variant narrowed to its type; primitive lexemes (decimals on their lexeme, calendar dates, the id grammar, canonicals); fixed[x] and pattern[x]; required bindings, through a tx-service when one is given and the value set expands offline, else through the offline expansions generated with the type tower; UCUM codes of quantities (a warning); value and pattern discriminator slicing, with an entry matched to exactly one slice held to the slice’s own children; and, unless invariants? is false, FHIRPath constraints — each at its element with %resource and %context bound, a violation only on a singleton false, the universal base keys (ele-1, ext-1, dom-*) and constraints on slices left unchecked (slice membership is not decided here). Invariants are on by default. Over the whole R5 core package they report nothing the package does not itself break (ten logical models without derivation, sdf-27; the fhir-types code system against the Shareable profile, scs-1). duplicates are the paths of duplicate JSON keys from read-fhir-json/duplicates, each an error. Anything undecidable (an unresolvable type, profile or value set, an unparseable expression) is not reported.
