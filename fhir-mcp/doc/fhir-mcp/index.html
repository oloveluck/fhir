fhir-mcp: a FHIR workspace for an agent🔗ℹ

A Model Context Protocol server. An agent works in a workspace: a directory of programs in the FHIR languages and FHIR JSON. Nine tools write, check, run and explain them against FHIR data. Each tool works the same way for every language: the file’s extension decides what it means. What one file defines, every other file sees by canonical. A CQL library uses a value set written in VCL, examples validate against profiles written in FSH, and a map’s results are validated as they are produced. Every problem is reported at a file, line and column. Part of the fhir family.

1 Quick start🔗ℹ

raco pkg install --link --auto fhir/fhir fhir/fhir-spec fhirpath vcl fhir/fhir-tx fhir/fhir-validation cql fml fsh sql-on-fhir fhir/fhir-lsp fhir/fhir-mcp

raco fhir-mcp --workspace my-workspace          # serve over stdio

For Claude Code or Claude Desktop, an entry in the MCP configuration:

{

  "mcpServers": {

    "fhir": { "command": "raco", "args": ["fhir-mcp", "--workspace", "/path/to/my-workspace"] }

  }

}

A workspace.yaml in the directory configures it. Every key is optional:

fhirVersion: 4.0.1                 # or 5.0.0; every language follows it (CQL's model is 4.0.1)

canonical: http://example.org/fhir # the base of what the workspace defines

packages:                          # FHIR packages in context: a .tgz path, or a name in fhir-spec / FHIR_PACKAGE_PATH

  - hl7.fhir.us.core-6.1.0

data: data/                        # a directory, a JSON file (a Bundle), or a FHIR server's base url

parameters:                        # CQL parameters, as CQL expressions

  Measurement Period: Interval[@2025-01-01T00:00:00.000, @2025-12-31T23:59:59.999]

allowRemoteWrites: false           # commit may write to a FHIR server only when true

--package adds packages and --data overrides data. A FHIR server that needs a token reads it from the environment variable FHIR_AUTHORIZATION, the whole header value. A token never goes in a file. raco fhir-mcp call <tool> ’<json>’ runs one tool from the shell (exit 1 when it fails), and raco fhir-mcp tools prints the schemas.

3 The tools🔗ℹ

tool

  

arguments

  

does

write

  

path, text

  

saves a file (empty text deletes it) and answers its problems in the same call; never outside the workspace or into the data

check

  

paths?

  

every problem, and the configuration: FHIR version, packages, data

run

  

path, entry?, over?, parameters?

  

a file against the data: a summary, the first rows, and a handle result://rN

query

  

language, text, …

  

the same without a file: fhirpath, cql (an expression is evaluated per patient), vcl, search (Type?params, on a FHIR server), view

explain

  

ref, subject, entry?

  

why one subject's answer is what it is (a result or a file)

describe

  

ref, offset?, limit?, against?

  

anything by reference: a result (paged, or compared with another), Type/id, a canonical, a type or element, an operation and its inputs, a fragment of a name

apply

  

operation, inputs?, resource?

  

any registered FHIR operation, in the workspace's context

stage

  

resources | result | path

  

a write prepared: each resource validated and compared with the data's copy (create, update and its changed paths, unchanged)

commit

  

stage

  

a stage written: to a data directory (a file per resource), or a FHIR server when allowed; a stage with errors is refused

Tool definitions are short (about 6 KB for the nine), and an operation’s inputs are read only when an agent asks for them with describe("$code").

4 Resources🔗ℹ

learn://workspace explains the workspace. learn://fsh, learn://cql, learn://fhirpath, learn://vcl, learn://fml, learn://sql-on-fhir and learn://search each give a cheat sheet, a worked example, common problems and links to the language’s official reference: the FHIR Shorthand specification, cql.hl7.org, FHIRPath N1, the VCL page of the IG guidance, the FHIR Mapping Language, sql-on-fhir.org and FHIR search. A test compiles every worked example. result://rN is a run’s whole result. fhir://guide/..., fhir://packages and fhir://definition/{kind}/{ref} serve the guides, the packages in context and their definitions. The prompts fsh-profile, fsh-instance and fix-workspace start an agent on common work.

5 Limits🔗ℹ

  • One workspace per server, one request at a time, stdio only. Results and stages live in the server’s memory.

  • CQL runs against the FHIR 4.0.1 model. An R5 workspace reports that at the library’s using.

  • A directory or file of JSON has no search engine. query("search") needs a FHIR server, and FHIRPath queries work everywhere.

  • Expansion uses the code systems in the packages. SNOMED CT and LOINC are not shipped, so a filter over them does not expand, though enumerated codes still work.

  • An update replaces the whole resource (PUT). The staged diff lists every path that changes, including elements the new resource leaves out.

  packages : (listof string?) = '()
The workspace in dir: workspace.yaml read, the packages and the core package of its FHIR version found, the data source opened, the operation modules loaded.

procedure

(with-hub h thunk) → any

  h : hub?
  thunk : (-> any)
Runs thunk with the hub’s packages and data source in context. The verbs’ procedures (hub-write!, hub-check, hub-run, hub-query, hub-explain, hub-describe, hub-apply, hub-stage!, hub-commit!) answer JSON or raise. Each language is reached through its <id>/workspace module, under the contract in fhir/lang/workspace.
