fhir-mcp: a FHIR workspace for an AI agent🔗

An AI agent such as Claude can do real work with health data, if it has the right place to do it: somewhere to write things down, a way to check them, a store for the data, and a record of what it did. fhir-mcp is that place. You say what you want ("record these lab results", "who has an HbA1c above 9 %?", "no result may be entered without a patient"); the agent writes it in one of FHIR’s languages, the tools check it and run it, and every change to the data is kept with who made it, when, why and from what.

The name: the Model Context Protocol (MCP) is the standard way an agent is given tools. This is an MCP server whose tools work on a workspace, a folder on your machine.

Part of the fhir family of FHIR languages and tools.

1 What you can do with it🔗

Things you can ask an agent that has a workspace, and what happens:

  • Record data. The agent writes the resources (a patient, a result), each is validated, and nothing invalid is stored.

  • Find its way around data it has not seen: what kinds of record there are, which codes they use and what those are called, what is recorded about one patient.

  • Ask questions of the data: find records by FHIR search, compute per patient with CQL ("the latest HbA1c for each patient"), turn records into tables and ask those in SQL.

  • Correct data by writing only what changes, with the reason kept.

  • Make rules the data must keep. A rule is a FHIR profile; once it is in force, a change that breaks it is refused, with the value that broke it.

  • See why. Why one patient got the answer they did; who changed a value, when, why, and what it was before.

  • Convert data: a filled-in form into a Patient, one shape into another, with a map.

  • Publish definitions: profiles, value sets and libraries with versions, kept in the same store, mirrored as text for git.

  • Stand up a server: a FHIR server over the same data, declared in a short file.

2 A first example🔗

1. Install the tools as the family’s front page describes.

2. Make a workspace.

$ raco fhir-mcp init clinic

wrote clinic/workspace.yaml

wrote clinic/.mcp.json

wrote clinic/CLAUDE.md

wrote clinic/.gitignore

workspace.yaml is its settings; .mcp.json is what tells Claude Code how to start the server; CLAUDE.md is a short note telling the agent where to begin. The data will live in clinic/fhir.db, created the first time something is stored.

3. Open the folder with your agent. With Claude Code, run claude inside clinic/: it reads .mcp.json and starts the server. For another client, the entry is:

{ "mcpServers": {

"fhir": { "command": "raco",

          "args": ["fhir-mcp", "--workspace", "/path/to/clinic"] } } }

4. Ask for something. For example: "Record a patient, Ann Lee, born 25 December 1974, and her HbA1c of 9.4 % on 1 September 2025. It is from the lab report." The agent writes the two resources in FHIR Shorthand:

Instance: ann

InstanceOf: Patient

* name.given = "Ann"

* name.family = "Lee"

* gender = #female

* birthDate = "1974-12-25"

 

Instance: a1c-1

InstanceOf: Observation

* status = #final

* code = http://loinc.org#4548-4 "Hemoglobin A1c"

* subject = Reference(Patient/ann)

* effectiveDateTime = "2025-09-01"

* valueQuantity = 9.4 '%'

It then stages them, which checks each one and says what would change, and commits the stage, which writes them:

stage  -> {"changes":[{"action":"create","resource":"Patient/ann"},

                       {"action":"create","resource":"Observation/a1c-1"}],"errors":0, …}

commit -> {"agent":"Dr Ng","reason":"entered from the lab report",

           "written":[{"version":"Patient/ann/_history/1", …},

                      {"version":"Observation/a1c-1/_history/1", …}], …}

5. Add a rule. "An HbA1c must be between 3 and 20 %." The agent writes a profile with that rule and puts it in force. From then on:

stage (an HbA1c of 94 %) ->

"errors": ["bad.fsh:7: Observation: a1c-range: An HbA1c is between 3 % and 20 %

            (found valueQuantity.value = 94)"]

The change is refused. The message names the rule, the value it found, and the line that wrote it.

6. Correct something, and look back. A result entered as 9.9 % should have been 8.9 %. The agent stages the correction ("changed": ["valueQuantity.value: 9.9 → 8.9"]) and commits it with the reason. The history of that result (describe ref=Observation/a1c-2/_history) then says, in short:

version 2  Dr Ng  "typing error: the report says 8.9"  value: 9.9 → 8.9

version 1  Dr Ng  "November result"                    created

Nothing is overwritten: every version is kept, each with who made it, when, why, and the text it was written from.

4 The nine tools🔗

The agent has nine tools, the same nine whatever the language. A person can run any of them from the shell too (Without an agent: from the shell).

Tool

  

What it does

write

  

saves a file and answers its problems in the same call, each at its line; can also bring a stored definition back as a file

check

  

lists every problem in the workspace; with the data too, every stored resource that breaks a rule

run

  

runs a file against the data and keeps the result under a name (result://…)

query

  

asks once without a file: a FHIRPath or CQL expression, a FHIR search, where a word occurs in the data, a value set, or SQL over the views, the tables and earlier results

explain

  

says why one patient or one resource got the answer it did, step by step

describe

  

reads anything back: what the data holds, one patient's record in brief, a result, a resource (as JSON or as FHIR Shorthand), its history, a definition, what an element or an operation is

apply

  

applies a FHIR operation ($validate, $expand, $transform, $evaluate-measure …)

stage

  

prepares a change to the data: each resource checked and compared with what is stored

commit

  

writes a stage, all of it or none, and records who, when, why and from what

The split between stage and commit is deliberate. Staging shows what would change and whether it is allowed, and changes nothing; only a stage with no errors can be committed.

6 Data the agent has not seen🔗

Most of the time the data is already there: a store loaded from a hospital’s export, with codes and shapes nobody has described to the agent. Three questions find its way around, and each answer names the next call.

What is here?

$ raco fhir-mcp call describe ref=data

{"data":"the SQLite store …/clinic/fhir.db (resources as JSONB; FHIR search; SQL)",

 "next":"describe ref=\"data/<Type>\": what a type's resources hold (its codes with their names,

         references, dates, elements); query language=find text=\"<words>\": where a word occurs

         and the search that finds it",

 "resources":7,"types":{"AuditEvent":1,"Observation":3,"Patient":2,"Provenance":1}}

describe ref=data/Observation then says what the Observations hold: the codes they use with their names and how often (4548-4 "Hemoglobin A1c" ×3), what they refer to, the span of their dates, the units of their values, and which elements every one of them carries.

Where is the thing I was asked about?

$ raco fhir-mcp call query language=find text=hemoglobin

{"columns":["where","value","text","resources","search","referencedBy"],"kind":"table",

 "result":"result://r1","summary":{"found":1},"total":1,"rows":[

{"where":"Observation.code, combo-code","value":"http://loinc.org|4548-4","text":"Hemoglobin A1c",

 "resources":3,"search":"Observation?code=http://loinc.org|4548-4","referencedBy":null}

]}

The words were found as the name of a code; the row gives the code and the search that finds its resources.

What is recorded about this patient?

$ raco fhir-mcp call describe ref=Patient/ann as=summary

{"holds":{"Observation":2},"is":{"birthDate":"1974-12-25","gender":"female","name":"Ann Lee"},

 "next":"query language=search text=\"<Type>?patient=Patient/ann&_sort=-date&_count=20\" for a

         page of one type, newest first …",

 "resource":"Patient/ann","trail":{"AuditEvent":1,"Provenance":1}}

With asof=<a time> the summary also says which hospital stays were open at that time, which is what "the current visit" means in a question asked at a time. A search answers a page of rows, one resource to a row, with what each holds (its code, value, date, subject) rather than its JSON, and total, every match. raco fhir guide data is the one page an agent reads for this.

7 Tables over the data🔗

Some questions are easier asked of a table. A view (a SQL on FHIR ViewDefinition) turns one kind of resource into rows; a .sql file is a table defined by one statement over the views, for what a single view cannot say, such as a join. Here two views, each a few lines of JSON, give the HbA1c results and the patients, and a statement joins them:

$ cat a1c.view.json

{"resourceType": "ViewDefinition", "name": "a1c", "status": "active", "resource": "Observation",

 "where": [{"path": "code.coding.where(system = 'http://loinc.org' and code = '4548-4').exists()"}],

 "select": [{"column": [

   {"name": "patient", "path": "subject.getReferenceKey(Patient)"},

   {"name": "date", "path": "effective.ofType(dateTime)"},

   {"name": "value", "path": "value.ofType(Quantity).value"}]}]}

$ cat patients.view.json

{"resourceType": "ViewDefinition", "name": "patients", "status": "active", "resource": "Patient",

 "select": [{"column": [

   {"name": "id", "path": "getResourceKey()"},

   {"name": "name", "path": "name.first().given.first() + ' ' + name.first().family"}]}]}

$ cat latest_a1c.sql

SELECT p.name, a.date, a.value

FROM a1c a JOIN patients p ON p.id = a.patient

WHERE a.date = (SELECT max(date) FROM a1c WHERE patient = a.patient)

$ raco fhir-mcp call query language=sql text="SELECT * FROM latest_a1c ORDER BY name" as=csv

name,date,value

Ann Lee,2025-11-03,8.9

Bo Ruiz,2025-10-10,6.1

latest_a1c is now a table like any other: SELECT name FROM latest_a1c WHERE value > 8 answers Ann Lee. Over a store, a view’s rows are computed once and kept until the data or the view changes, so a view over a million resources is slow the first time only. This is also how an agent works with data whose users think in a relational schema: it defines the schema’s tables over the FHIR store once, and queries written for that schema then run as they stand. raco fhir guide tables is the agent’s page for it.

8 Saying only what changes🔗

To change a stored resource the agent does not send the resource back. It names it and writes the rules that change:

$ cat ../fix.fsh

Instance: Observation/a1c-2

* valueQuantity = 8.7 '%'

* note.text = "typing error: the report says 8.7"

$ raco fhir-mcp call stage fsh=@../fix.fsh

{"changes":[{"action":"update","changed":["note: added [{\"text\":\"typing error: the report says 8.7\"}]",

 "valueQuantity.value: 8.9 → 8.7"],"resource":"Observation/a1c-2"}],"errors":0,

 "next":"commit stage=stage-2 writes the 1 change(s) to the store fhir.db","stage":"stage-2"}

The rules are laid over the stored resource, the result is checked like any other change, and the record of the commit keeps the three lines as they were written. After the commit the table above reads Ann Lee,2025-11-03,8.7.

9 Rules the data must keep🔗

A rule is a FHIR profile, written in FHIR Shorthand: "an HbA1c is between 3 and 20 %", "a blood pressure has a systolic and a diastolic value in mm[Hg]", "every result names its patient". Putting it in force is one line in workspace.yaml (profiles:), or write … enforce:=true, or a global: line in the implementation guide.

Once in force, a rule is applied whenever data is staged, so a change that breaks it cannot be committed. check data:=true applies the rules to everything already stored and counts what breaks which rule: the way to find out what a new rule would catch. The workspace guide (raco fhir guide workspace) has a cookbook of common rules, each one tested.

10 The record of every change🔗

Each commit leaves two FHIR resources in the store beside the data: a Provenance, which says which versions it wrote, who the agent was, the reason given, and the source text it wrote them from (kept whole, with its fingerprint); and an AuditEvent, the plain log line that it happened. With audit: all in the settings, every run and query leaves an AuditEvent too.

Because the record is data, it can be asked about like any other:

$ raco fhir-mcp call query language=sql \

    text="SELECT type, id, versionId, agent, reason, at FROM trail ORDER BY recorded" as=csv

type,id,versionId,agent,reason,at

Patient,ann,1,Dr Ng,entered from the lab report,../results.fsh:1

Observation,a1c-1,1,Dr Ng,entered from the lab report,../results.fsh:14

Observation,a1c-2,1,Dr Ng,November result,../good.fsh:7

Observation,a1c-2,2,Dr Ng,typing error: the report says 8.9,../fix.fsh:7

trail is one row for each version a commit wrote; at is the file and line it came from. describe ref=Observation/a1c-2/_history gives one resource’s versions with what changed in each.

11 Definitions, versions and git🔗

Profiles, value sets, libraries and maps are FHIR resources too, and the store keeps them with the data. An implementation guide (sushi-config.yaml) gives them a shared name, version and status: draft while you work, active once released. A released definition does not change; changing it means a new version, and the old one is kept.

The files are working copies. Delete one and the definition is still in the store; write path=lab.fsh ref=<its address> brings it back as text. Because git cannot compare a database, every commit of a definition also rewrites export/: the same definitions as text files, which is what you put in git. raco fhir-mcp export --check tells a build whether that folder is up to date.

raco fhir guide ig is the full account: versions, pinning a version, what depends on what.

12 Guides the agent reads🔗

The server carries guides written for an agent: short, dense, every example tested. An agent reads them as learn://<topic>; you can print the same text with raco fhir guide <topic>.

fhir

  

FHIR itself: which resource holds which fact, the shapes that recur, the usual code systems

workspace

  

the workspace: the tools, which language for which question, rules, the record of changes

data

  

reading a store in one page: what a type holds, a patient as of a time, words to codes, search, rows

tables

  

a relational schema defined over the data, as views and SQL

fsh, cql, fhirpath, vcl, fml, sql-on-fhir

  

each language: a cheat sheet, a worked example, common problems

ig

  

the implementation guide: definitions, versions, the store in git

capability

  

FHIR servers you declare

search

  

FHIR search

racket

  

the same languages in a Racket program, with no server

The fhir skill in the repository (.claude/skills/fhir/SKILL.md) is where an agent starts: which tool for which job, and a whole session from creating data to a table.

13 Settings: workspace.yaml🔗

Every line is optional.

fhirVersion: 4.0.1                 # or 5.0.0; every language follows it

canonical: http://example.org/fhir # where the addresses of your definitions begin

data: fhir.db                      # the store; or a folder of JSON, or a FHIR server

export: export/                    # where the definitions are written as text for git

packages:                          # published FHIR packages to work against

  - hl7.fhir.us.core-6.1.0

profiles:                          # the rules in force, by resource type

  Observation: http://example.org/fhir/StructureDefinition/a1c-result

audit: commits                     # or all: also record every run and query

parameters:                        # values for CQL parameters

  Measurement Period: Interval[@2025-01-01T00:00:00.000, @2025-12-31T23:59:59.999]

allowRemoteWrites: false           # a FHIR server is only written to when this is true

models:                            # a CQL data model made from your own logical models

  Clinic: http://example.org/fhir patient=Member birthDate=born version=1.0

When there is a sushi-config.yaml, the FHIR version, the canonical, the packages and the rules it states are taken from it, since they belong to the guide.

A FHIR server that needs a token reads it from the environment variable FHIR_AUTHORIZATION (the whole header value). A token is never kept in a file.

14 Without an agent: from the shell🔗

Every tool can be run by hand, which is how you check what an agent did, or script it.

raco fhir-mcp call stage fsh=@results.fsh     # one tool; @file passes a file's text

raco fhir-mcp call commit stage=latest reason="from the lab report" agent="Dr Ng"

raco fhir-mcp call describe ref=Observation/a1c-2/_history

raco fhir-mcp batch session.txt                # many calls in one go, one per line

raco fhir-mcp tools                            # the nine tools and their arguments

raco fhir-mcp export --check                   # is export/ up to date?

Run them inside the workspace folder, or add --workspace <dir>. An argument is name=value; name=@file gives a file’s contents; name:=<json> gives a number, true or false, or a JSON object. A call that finds errors exits with status 1.

The first call starts a background process for the workspace that answers the next ones: they take about a third of a second instead of one to four. It reads the workspace afresh for every call, so its answers are the ones a separate process would give, and it stops after five minutes without a call, when the workspace folder is removed, or when the installed code changes. Set FHIR_MCP_DAEMON=0 to run every call in a process of its own.

15 Words used here🔗

  • MCP (Model Context Protocol): the standard by which an AI agent is offered tools.

  • Workspace: the folder an agent works in, with its settings, files and store.

  • Store: the SQLite database (fhir.db) that holds the resources and their history.

  • Resource: one FHIR document, such as a Patient or an Observation.

  • Profile: a set of rules for a kind of resource. Here, the rules the data must keep.

  • Stage, commit: a change prepared and checked, then written.

  • Provenance, AuditEvent: the FHIR resources that record who changed what and why, and that something happened.

  • Implementation guide: the named, versioned collection of a workspace’s definitions.

  • Canonical: the web address that names a definition.

  • View: a SQL on FHIR ViewDefinition, which turns resources into the rows of a table.

  • Census: what describe ref=data answers: the kinds of resource in the data, and for one kind its codes, references, dates and elements.

16 Limits🔗

  • One workspace to a server, one request at a time, over standard input and output.

  • CQL’s FHIR model is version 4.0.1; a library that uses FHIR in a 5.0.0 workspace is told so at its using line.

  • Listing a value set’s codes uses the code systems in the packages. SNOMED CT and LOINC are not shipped, so a value set defined by a rule over them cannot be listed, though one that lists its codes works.

  • Each stored version is a whole resource. A change can be given as only the rules that differ (Saying only what changes); given as a whole resource, it replaces the stored one, and the staged change lists every path that differs, including what the new version leaves out.

  • SQL is one reading statement (SELECT, WITH, VALUES); it cannot change the data.

  • FHIR search follows one step of a chain (subject.name=…, medication.code=…) but not a reverse chain (_has) or a longer one; such a search is refused rather than answered wrongly. The same question is a CQL library.

  • A server declared in the workspace (*.capability.rkt) runs in a process of its own and speaks FHIR R6; it stops when the workspace’s server stops.

  • Data kept as a folder of JSON files or on a FHIR server can be read, searched and written, but the history of versions and SQL over the stored resources themselves need the store (data: fhir.db).

17 How it is tested🔗

Every session in the guides and in the fhir skill is replayed by a test exactly as written: the commands, and the answers they quote. Each rule in the cookbook is tested with a resource that passes and one that is refused. A further test runs every command these documents name.
