fhir-server: FHIR servers generated from specs🔗ℹ

A FHIR server from a specification. make-ig-server generates a whole server from an Implementation Guide package: its CapabilityStatement gives the types, interactions, search parameters, includes and operations; its profiles validate every write; what the IG asks for and the server does not do is reported as a gap (US Core has none). Under it, #lang fhir/capability declares an app of your own and derives its CapabilityStatement, a small HTTP server maps the FHIR REST grammar onto it, and an embedded SQLite store keeps the data (versioned CRUD, type-driven search, transactions, audit and provenance). Part of the fhir family.

1 Quick start🔗ℹ

1. Install. The packages are not on the Racket package server yet; clone the repositories side by side and install from source:

raco pkg install --link --auto fhir/fhir fhir/fhir-spec fhirpath vcl fhir/fhir-tx fhir/fhir-validation cql fhir/fhir-server

2. Serve an Implementation Guide. A package in fhir-spec, a .tgz, or a path; the IG’s examples are loaded first, through validation.

$ raco fhir-server serve-ig hl7.fhir.us.core --port 8080

$ curl localhost:8080/metadata

$ curl 'localhost:8080/Patient?name=Chalmers&_include=Patient:general-practitioner'

$ curl -X POST localhost:8080/Observation -d @bad.json        # 422 with an OperationOutcome

3. See what the IG asks for that is not served: raco fhir-server serve-ig hl7.fhir.us.core –gaps.

A package written by raco fsh –pack serves the same way: raco fhir-server serve-ig my-ig-0.1.0.tgz –capability my-server, with its dependencies resolved from fhir-spec.

2 Using it🔗ℹ

2.1 Command line🔗ℹ

raco fhir-server serve-ig <package> [–port n]

  

a server generated from the IG; its examples loaded

–capability <id|url>

  

which server CapabilityStatement, when the IG ships several

–load <dir|file>

  

Bundles, resources or .cql files (as Library resources)

–db store.db

  

keep the store between runs (SQLite)

–gaps

  

print what the IG asks for that is not served, and stop

–bearer <token>, –tz-offset ±hh:mm, –no-examples, –no-validate

  

a static token; the evaluation timezone; skip the examples or the write validation

raco fhir-server serve app.rkt [port]

  

a #lang fhir/capability app

raco fhir-server load store.db data/

  

prepopulate a store

raco fhir-server evaluate-measure store.db <Measure> –period-start d –period-end d [–subject Patient/x]

  

a MeasureReport from the store

2.2 A server from an IG, in Racket🔗ℹ

(require fhir/store/fhir-sqlite fhir/store/ig-server fhir/http/server)
(define store (open-fhir-store "us-core.db"))
(define srv (make-ig-server store (ig-package-path "hl7.fhir.us.core") #:capability "us-core-server"))
(load-ig-examples! srv)
(ig-server-gaps srv)                                   ; (listof gap)
(define stop (serve-app (ig-server-app srv) #:port 8080))

2.3 A server you declare🔗ℹ

#lang fhir/capability: three forms among plain Racket definitions. The lang derives the CapabilityStatement and the OperationDefinitions, so /metadata cannot drift from the code. Interactions and parameter types are checked against FHIR’s code sets when the module compiles.

#lang fhir/capability

(server #:mode "server" #:status "active" #:url "http://localhost/fhir")

 

(resource Patient

  #:interactions (read create update delete search-type)

  #:search-params ([gender token "Patient.gender"] [family string "Patient.name.family"]))

 

(operation $ping #:system #:in ([message string 0 1]) #:out ([result string 1 1])

  #:handler ping-handler)

 

(define (ping-handler in req)

  (define msg (let ([m (hash-ref in "message" '())]) (if (pair? m) (car m) "pong")))

  (Parameters (parameter (ParametersParameter (name "result") (valueString msg)))))

  • (server #:mode "server" #:status s #:url u #:fhir-version v ...), once; every keyword optional.

  • (resource Type #:interactions (...) #:search-params ([name type "FHIRPath"] ...) #:repository r #:profile url). Without #:repository the resource gets an in-memory one implementing exactly the declared interactions, with search by each parameter’s FHIRPath.

  • (operation $code #:on Type #:in ([name type min max] ...) #:out (...) #:handler h), or #:system in place of #:on Type: the handler is (lambda (inputs request) node). (operation "ValueSet/$expand") exposes an existing fhir/operation value under its own definition.

racket app.rkt prints /metadata; raco fhir-server serve app.rkt 8080 serves it. The module provides app, capability-statement and operation-definitions; (dispatch app (search-request 'Patient '((gender . "male")))) runs a request in process.

2.4 Operations over HTTP🔗ℹ

Any fhir/operation values, with a CapabilityStatement derived from them:

(require fhir/capability/operations fhir/conformance/operations fhir/terminology/operations)
(define stop (serve-operations (cons $validate terminology-operations) #:port 8080
                               #:terminology-capabilities (current-terminology-capabilities)))

2.5 The store🔗ℹ

The SQLite store behind the generated servers is usable on its own: versioned CRUD with history, search driven by an IG’s SearchParameters, transaction Bundles.

(require fhir/store/fhir-sqlite fhir/store/fhir-engine fhir/store/bundle fhir/store/serve
         fhir/store/ig-params)
(define store (open-fhir-store "fhir.db"))
(define catalog (search-params-from-package (spec-package-path "hl7.fhir.r5.core.tgz")))
(fhir-create! store patient #:search-params catalog)
(fhir-search store "Patient" '(("gender" . "male")) #:search-params catalog)
(process-bundle! store transaction-bundle #:search-params catalog)
(serve-app (make-store-app store #:package core-tgz #:types '(Patient Observation) #:audit? #t) #:port 8080)

3 Limits🔗ℹ

What a FHIR server can be asked for and this one does not do, from the code. The generated server reports the first group as gaps against an IG’s CapabilityStatement; the rest it does not report.

  • Search. Token, reference, string, date, number, quantity and uri parameters, with prefixes, :missing, :exact and :contains (string), :not (token), comma OR, _id, _lastUpdated (second precision), _count as a limit, _include and _revinclude (Source:param[:Target], Source:*). Absent: composite and special parameters, chaining (patient.name=), _has, _sort, paging links and _offset, _total (the Bundle’s total is the page size when _count cuts it), _summary, _elements, _filter, _text, _content, :iterate, the other modifiers (:text, :above, :below, :in, :identifier), system-level search, POST /Type/_search, and the parameters whose base is Resource (_tag, _profile, _security: the catalog is keyed by the concrete type). Quantity search converts no units. String search indexes HumanName and Address, not other complex types. Searchset entries carry no fullUrl.

  • A parameter the server cannot run is dropped, as FHIR’s lenient default allows, and the result is broader than asked; the dropped names come back only from fhir-search/ignored, not as an OperationOutcome in the Bundle, and there is no Prefer: handling=strict.

  • Headers. The router sees method, path, query and body only. So no conditional create, update or delete (If-None-Exist, PUT /Type?param), no If-Match or ETag, no If-Modified-Since, Prefer or Accept; responses carry no ETag, Last-Modified or Location. Update is an upsert that answers 200, never 201. A create with an existing id is a 500, not a 409.

  • History. Instance and type level with _since and _count; no system level, no _at, no paging, and a delete leaves no entry (history keeps the versions, not the deletion).

  • Transactions. Over a store: atomic transaction and batch, urn: fullUrls rewritten for POST entries; no GET, HEAD or PATCH entries, no conditional references or ifNoneExist/ifMatch, response entries without the resource. In the generated IG server the transaction endpoint writes through the store directly: it does not validate against profiles or apply the IG’s per-type interaction restrictions, as REST writes do. An app without a store (the operations app) answers a batch by routing each entry through the router, operations included, and has no transaction.

  • PATCH is JSON Patch only; no FHIRPath Patch.

  • Transport. JSON only (no XML, _format or content negotiation), HTTP/1.1 with one request per connection and Content-Length bodies, no TLS, no CORS, no HEAD or OPTIONS. The 401, 409 and 422 status lines carry the wrong reason phrase.

  • Security. One static bearer token or nothing; no SMART on FHIR, OAuth, scopes or per-resource access control. An IG’s rest.security is copied into /metadata unchanged.

  • Operations. Only registered operations are served: $validate (type and instance levels, mode ignored), $expand, $validate-code, $lookup, $translate, $snapshot, $evaluate-measure, and $docref as a search over existing DocumentReferences. No compartments or $everything, subscriptions, bulk export or GraphQL. System-level operations are served but not advertised.

  • The CapabilityStatement a generated server publishes is the IG’s own, trimmed to what runs; its conditionalCreate, conditionalUpdate, versioning and updateCreate flags are left as the IG declared them, history-system and search-system are dropped without a gap, and transaction and batch are always added.

  • The in-memory repository of #lang fhir/capability searches by equality of FHIRPath values, with no modifiers or prefixes, keeps no history, and answers vread with the latest version. make-store-app serves history and PATCH but advertises neither.

4 Reference🔗ℹ

#lang fhir/capability🔗ℹ

 #lang fhir/capability package: fhir

The server, resource and operation forms, as above; provides app, capability-statement and operation-definitions. Everything from fhir/capability/runtime, fhir/capability/derive and fhir/r6/types is in scope. An inline (operation $code … #:handler h) also defines $code as a fhir/operation value (declared-operation): the same handler, applied in-process with the inputs and an in-process request, registered by its canonical and provided by the module — a pipeline declared once is served and callable (($code #:name value), (apply-operation "$code" …)).

fhir/store/fhir-engine🔗ℹ

 (require fhir/store/fhir-engine) package: fhir-server

Versioned CRUD and search over the store. Every write stamps meta.versionId and meta.lastUpdated, keeps the version in an immutable history, and re-indexes the resource in the same transaction. Search is type-driven by the catalog: each parameter’s SearchParameter type picks its index (token, reference, string, date, number, quantity, uri) and matching rules, with prefixes, modifiers, _id, _lastUpdated, _count, and comma as OR; unknown parameters are ignored and reported by fhir-search/ignored.
