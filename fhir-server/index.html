9.3

fhir-server: FHIR servers🔗

Health data is exchanged as FHIR resources: a patient, a lab result, a prescription, each a small JSON document. A FHIR server is where such resources are kept and reached over the web. It does four things. It stores a resource you send it, and keeps every earlier version. It lets you read one back by its address. It lets you search: all the lab results of this patient, every patient born before 1980. And it checks what is written, refusing a resource that breaks FHIR’s rules.

Every FHIR server also publishes a description of itself, called its CapabilityStatement: which kinds of resource it holds, what can be done with each, which searches it answers. Other software reads that description to learn how to talk to it. In this package the description is never written by hand. It is worked out from what the server really does, so the two cannot disagree.

This package makes FHIR servers in two ways. One command builds a whole server from a published Implementation Guide, with nothing to write. Or you declare a server of your own in a short file: which resources, which searches, your own operations. Both keep their data in a single SQLite file. The command is raco fhir-server.

These servers are for developing and testing against a specification. They are not built to face the internet: see Limits.

Part of the fhir family of FHIR languages and tools.

1 What you can do with it🔗

  • Start a small server of your own and call it: A first example.

  • Run a server that follows a published guide such as US Core, loaded with the guide’s examples: A server from an Implementation Guide.

  • Declare exactly what your server offers: resources, searches, and calculations of your own as operations (A server you declare).

  • Decide what happens to a search the server cannot apply: Strict and lenient search.

  • Fill the store from files and query it with SQL: The store.

  • Compute a quality measure over the stored patients: Measures.

  • Use any of it from a program: From a program.

2 A first example🔗

The smallest useful server: it keeps patients and observations, searches them, validates what is written, and offers one operation of its own.

1. Install the tools as the family’s front page describes. The command is then raco fhir-server (or fhir-server, if you built the standalone tools). It needs the system’s SQLite library.

2. Write the server, as study.capability.rkt:

#lang fhir/capability

(require (only-in fhir/conformance/operations $validate))

(server #:store "study.db" #:search-handling "strict"

        #:references "checked")

(resource Patient #:interactions (read create search-type) #:search-params ([gender token] [birthdate date]))

(resource Observation #:interactions (read create search-type) #:search-params ([patient reference] [code token]))

(define (double-handler in req)

  (Parameters (parameter (ParametersParameter (name "doubled") (valueDecimal (* 2 (car (hash-ref in "x"))))))))

(operation $double #:system #:in ([x decimal 1 1]) #:out ([doubled decimal 1 1]) #:handler double-handler)

(operation $validate)

Reading it from the top:

  • #lang fhir/capability says the file is a server declaration.

  • (server …) sets things for the whole server. The data goes in study.db, beside the file. The other two settings make it careful, as a server of patient data should be: it refuses a search it cannot apply in full (Strict and lenient search), and refuses an observation about a patient it does not hold.

  • Each (resource …) names a kind of resource the server holds, what may be done with it (interactions: read one, create one, search), and what it can be searched by.

  • (operation $double …) is an operation: a named service beyond storing and searching, here one that doubles a number. Its inputs and outputs are declared with their types; double-handler is the code that does the work. It is a toy; a real one would compute a score or a dose.

  • (operation $validate) offers FHIR’s standard validation operation, which the require line brought in.

You can also print this starting file instead of typing it: raco fhir guide capability --block smallest > study.capability.rkt.

3. Check it. This compiles the declarations and says what the server will offer:

$ raco fhir-server check study.capability.rkt

ok  study.capability.rkt  (FHIR 6.0.0-ballot4)

  Patient: read, create, search-type; search by gender, birthdate

    $validate

  Observation: read, create, search-type; search by patient, code

    $validate

  $double (system)

(what an operation answers is checked when it runs: serve it and call each once)

4. Start it. --port 0 takes any free port:

$ raco fhir-server serve study.capability.rkt --port 0

FHIR server on http://localhost:43493  (Ctrl-C, or kill 9711, to stop)

search: strict (a parameter the app does not declare is refused, 400)

store: …/study.db (created on the first request)

The first line is the one to read: it gives the address the server answers at, with the port it took, and the number to stop it by. The server keeps running; use another terminal for the next steps, with the address your own server printed.

5. Ask what it supports. Every FHIR server answers at /metadata with its CapabilityStatement. This one was derived from the file:

$ curl http://localhost:43493/metadata

{"resourceType":"CapabilityStatement","status":"active", … "fhirVersion":"6.0.0-ballot4", …

 "rest":[{"mode":"server","resource":[

   {"type":"Patient","interaction":[{"code":"read"},{"code":"create"},{"code":"search-type"}],

    "searchParam":[{"name":"gender","type":"token"},{"name":"birthdate","type":"date"}],

    "operation":[{"name":"$validate", …}]}, …

6. Store a patient. Send the resource with POST to the address of its type:

$ curl -i -X POST http://localhost:43493/Patient -H 'Content-Type: application/fhir+json' \

    -d '{"resourceType":"Patient","gender":"female","birthDate":"1974-12-25","name":[{"family":"Lee","given":["Ann"]}]}'

HTTP/1.1 201 Created

Content-Type: application/fhir+json; charset=utf-8

Location: http://localhost:43493/Patient/758d3b7eabba0b5caa0f666c6f64eaa0/_history/1

…

{"resourceType":"Patient","id":"758d3b7eabba0b5caa0f666c6f64eaa0","meta":{"versionId":"1","lastUpdated":"2026-11-13T14:28:02Z"},"name":[{"family":"Lee","given":["Ann"]}],"gender":"female","birthDate":"1974-12-25"}

201 Created means it was stored. The server gave the patient an id and a version number, and Location is the address of exactly this version.

7. Read it back, and search. A resource’s address is its type and id. A search is the type, a question mark, and what to match:

$ curl http://localhost:43493/Patient/758d3b7eabba0b5caa0f666c6f64eaa0

{"resourceType":"Patient","id":"758d3b7eabba0b5caa0f666c6f64eaa0", … "gender":"female","birthDate":"1974-12-25"}

 

$ curl 'http://localhost:43493/Patient?gender=female'

{"resourceType":"Bundle","type":"searchset","total":1, … "entry":[{"fullUrl":"http://localhost:43493/Patient/758d3b7eabba0b5caa0f666c6f64eaa0","resource":{"resourceType":"Patient", …},"search":{"mode":"match"}}]}

A search answers with a Bundle, FHIR’s envelope for a list of resources. total is how many matched; each entry is one of them. Patient?birthdate=lt1980 finds the same patient: lt means "before".

8. Send something wrong. A French gender and a thirtieth of February:

$ curl -X POST http://localhost:43493/Patient -H 'Content-Type: application/fhir+json' \

    -d '{"resourceType":"Patient","gender":"femme","birthDate":"1974-02-30"}'

{"resourceType":"OperationOutcome","issue":[

 {"severity":"error","code":"processing","diagnostics":"Patient does not conform to its base type: nothing was written"},

 {"severity":"error","code":"code-invalid","diagnostics":"code `femme` not in required value set http://hl7.org/fhir/ValueSet/administrative-gender; it holds female, male, other, unknown","expression":["Patient.gender"]},

 {"severity":"error","code":"invalid","diagnostics":"'1974-02-30' is not a valid date (February 1974 has 28 days)","expression":["Patient.birthDate"]}]}

The status is 422 and the answer is an OperationOutcome, FHIR’s report of problems: one entry per problem, with the place. Nothing was stored.

9. Call the operation. An operation’s address starts with a dollar sign (quote it, or the shell will read it as a variable):

$ curl 'http://localhost:43493/$double?x=2.5'

{"resourceType":"Parameters","parameter":[{"name":"doubled","valueDecimal":5.0}]}

10. Stop it, by the number in its first line: kill 9711, or Ctrl-C in its own terminal. The data stays in study.db; start the server again and the patient is still there.

A mistake in the file is reported by check, at its line, before anything is served. Write search for search-type and birthDate for birthdate:

$ raco fhir-server check study.capability.rkt

study.capability.rkt:6:50: resource: unknown restful interaction search (did you mean `search-type`?); a resource takes read, vread, update, patch, delete, history-instance, history-type, create, search-type

study.capability.rkt:5:0: resource Patient: search parameter `birthDate`: FHIR defines none of that name for Patient (did you mean `birthdate`?); give its FHIRPath: [birthDate date "…"]

3 What a server says about itself🔗

The CapabilityStatement is how a client finds out, without trying, what a server can do. It lists each resource type with its interactions, the names and kinds of its search parameters, and its operations. A client that wants to search observations by date looks there first.

A hand-written statement goes stale: someone adds a search, or removes one, and forgets the description. Here that cannot happen, in either kind of server.

  • For a server you declare, the statement is derived from the declarations, and the server does what the declarations say: an interaction that is not declared is refused (405), and a search uses exactly the declared parameters.

  • For a server generated from a guide, the statement starts as the guide’s own and is trimmed to what this server executes. What was trimmed is not hidden: it is listed for you as a gap (A server from an Implementation Guide).

Each operation has a description of its own as well, an OperationDefinition: its inputs and outputs with their types. These are derived too, and served at /OperationDefinition (all of them) and /OperationDefinition/double (one).

4 A server from an Implementation Guide🔗

An Implementation Guide (IG) is a published agreement on how to use FHIR for one purpose: US Core for health records in the United States, the International Patient Summary, mCODE for cancer data. It contains profiles (stricter rules for particular resources), the search parameters and operations a conforming server must offer, a CapabilityStatement saying so, and example resources. It is distributed as a package, one .tgz file.

That is a complete specification of a server, and serve-ig builds the server from it:

$ raco fhir-server serve-ig hl7.fhir.us.core --port 8080

loaded 255 example(s); 0 rejected by validation

0 IG requirement(s) not met (raco fhir-server serve-ig hl7.fhir.us.core --gaps); 0 of them SHALL

FHIR server for hl7.fhir.us.core on http://localhost:8080  (store: /var/tmp/fhir-ig-17945801221794580122105.db; Ctrl-C, or kill 3282, to stop)

It takes about fifteen seconds to start. Everything came from the package:

  • The FHIR version. US Core is written for FHIR R4, so this is an R4 server.

  • What it serves. The guide’s CapabilityStatement names 31 resource types, with the interactions and search parameters for each. /metadata answers that statement.

  • How search works. Each search parameter is defined in the guide or in FHIR itself by a formula saying where in a resource its value is found; the server indexes resources by those formulas.

  • What it accepts. Every resource written is validated against FHIR’s rules for its type and against the profiles it claims.

  • What is in it. The guide’s own examples are loaded first, each through the same validation; a guide’s examples are a ready set of test data.

Try it. The examples include two patients named Shaw, and an encounter can bring its patient along (_include):

$ curl 'http://localhost:8080/Patient?family=Shaw'

{"resourceType":"Bundle","type":"searchset","total":2, … }      (Patient/deceased-example, Patient/example)

 

$ curl 'http://localhost:8080/Encounter?patient=Patient/example&_include=Encounter:patient'

{"resourceType":"Bundle","type":"searchset","total":3, … }      (three Encounters, and Patient/example marked "include")

A patient that claims the US Core profile and lacks the identifier it requires is refused, with status 422:

$ curl -X POST http://localhost:8080/Patient -H 'Content-Type: application/fhir+json' -d '

{"resourceType":"Patient","meta":{"profile":["http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient"]},

 "gender":"female","name":[{"family":"Lee","given":["Ann"]}]}'

{"resourceType":"OperationOutcome","issue":[{"severity":"error","code":"processing","diagnostics":"Patient does not conform to http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient"},{"severity":"error","code":"required","diagnostics":"minimum required = 1, but found 0","expression":["Patient.identifier"]}]}

Note what "claims" means: the resource lists the profile in its meta.profile. The same patient without that line is a valid plain Patient and is stored. The server holds a resource to the profiles it says it follows, not to every profile the guide has for its type.

4.1 Gaps: what the guide asks for that is not served🔗

A guide may require something this server does not do. Rather than advertise it anyway, the server leaves it out of /metadata and reports it. --gaps prints the list and stops. US Core has none, and the command says so; the International Patient Summary has one:

$ raco fhir-server serve-ig hl7.fhir.us.core --gaps

hl7.fhir.us.core: no unmet requirement (every SHALL, SHOULD and MAY of its CapabilityStatement is served)

$ raco fhir-server serve-ig hl7.fhir.uv.ips --gaps

Patient operation summary SHOULD operation not implemented

Each line is the resource type, the kind of thing (an interaction, a search parameter, an include, an operation), its name, how strongly the guide asks for it (SHALL, SHOULD or MAY), and why it is not served. The start-up line counts them, and how many are SHALL.

4.2 Which guide, and the options🔗

The guide is named by a package that comes with the tools (hl7.fhir.us.core, with or without .tgz) or by the path of a .tgz you downloaded from packages.fhir.org. Those that come with the tools and describe a server are US Core (hl7.fhir.us.core is 9.0.0; hl7.fhir.us.core-8.0.0 and hl7.fhir.us.core-6.1.0), the International Patient Summary (hl7.fhir.uv.ips), mCODE (hl7.fhir.us.mcode-4.0.0), CQF Measures (hl7.fhir.us.cqfmeasures-5.0.0) and CRMI (hl7.fhir.uv.crmi-2.0.0). A guide’s dependencies on other packages are found the same way. A package with no server CapabilityStatement cannot be served, and the command says so.

A guide you wrote yourself in FHIR Shorthand works too: raco fsh <dir> --pack writes the package (see fsh), and serve-ig serves it.

5 A server you declare🔗

When no guide describes the server you want, you write its declaration, as in A first example. The file is a list of three kinds of form, in any order, among ordinary Racket definitions for the code of your operations. This section says what each form can express. The repository’s fhir-server/capability/guide.md goes further, with complete worked operations (an eGFR calculator with typed, bounded inputs; an output with a unit); raco fhir guide capability prints it.

A declared server speaks FHIR R6, the version now being finalised. For the common resources (Patient, most of Observation) the JSON is the same as in R4.

5.1 server: the whole server🔗

One (server …) form, every setting optional and each value a text in quotes:

setting

  

meaning

#:store "fhir.db"

  

the SQLite file the data is kept in, beside the declaration; without it, a temporary file removed when the server stops

#:search-handling "strict"

  

refuse a search with a parameter the server cannot apply (default "lenient"; Strict and lenient search)

#:references "checked"

  

refuse a resource that refers to another the server should hold and does not (default "unchecked")

#:warnings "refuse"

  

refuse a resource whose validation gives warnings, not only errors (default "accept")

#:url, #:name, #:description, #:status, #:date

  

what the CapabilityStatement says of the server: its address, name and so on

#:mode, #:format

  

the statement’s mode ("server" unless you say "client") and formats (JSON); leave them out

5.2 resource: what is stored🔗

(resource Patient

#:interactions (read create update delete search-type history-instance)

#:search-params ([gender token] [birthdate date] [family string "name.family"]))

Interactions are FHIR’s names for what can be done with a resource:

An interaction you did not declare is refused with status 405, and a resource type you did not declare with 404.

Search parameters are what a resource can be found by. FHIR defines a standard set for each type, with names such as gender, birthdate, family, identifier for a Patient and patient, subject, code, value-quantity for an Observation. [gender token] asks for FHIR’s own parameter of that name; the second word is its kind, which decides how values are compared:

kind

  

matches

  

example

token

  

a code, optionally with its system

  

code=http://loinc.org|4548-4

string

  

the start of a text, ignoring case and accents

date

birthdate=lt1980

reference

patient=Patient/ann

number

a number with a unit

  

value-quantity=gt9

uri

A date written without a time zone means the day, or the time, as each record wrote it: date=2116-12-17 finds a reading recorded as 2116-12-17T23:52:00-05:00, though in UTC that moment is on the 18th. A date written with a zone (date=ge2116-12-17T00:00:00Z) is that instant, whatever zone a record was written in.

A name FHIR does not define for that type, or the wrong kind for it, is an error when you check the file, with the nearest real name. For a search of your own invention, add the place in the resource to look, as a FHIRPath expression: [family string "name.family"].

Every type also answers _id, _lastUpdated, _count (how many to return), _offset and _sort. A reference search can pull the referenced resources into the same answer with _include (and the resources that refer to the matches with _revinclude). A code can be searched by what it is called: Observation?code:text=hemoglobin finds the observations whose code’s display, or whose concept’s text, holds the word, in any case. (FHIR asks :text for text that begins with the words; here they may stand anywhere in it.)

5.3 operation: a service of your own🔗

(operation $bmi #:system

  #:in ([weight decimal 1 1] [height decimal 1 1])

  #:out ([bmi decimal 1 1])

  #:handler bmi-handler)

 

(define (bmi-handler in req)

  (define (input k) (car (hash-ref in k)))

  (define m (/ (input "height") 100))

  (define bmi (/ (input "weight") (* m m)))

  (Parameters (parameter (ParametersParameter (name "bmi") (valueDecimal (/ (round (* bmi 10)) 10.0))))))

  • Where it is called. #:system puts it at the top (/$bmi); #:on Patient at a type (/Patient/$bmi).

  • Inputs and outputs are [name type min max]: the type is a FHIR type (integer, decimal, boolean, string, code, date, Quantity, Patient …), and min max say how many: 1 1 required, 0 1 optional, 0 * a list. An input may add #:min/#:max (a number’s allowed range), #:binding (the value set a code must come from) and #:documentation (what it means, with its unit).

  • The handler is a function of the inputs and the request. in maps each input’s name to the list of its values, already of the declared type: a decimal arrives as a number. A Quantity or another value with parts arrives whole, and (field q 'value), (field q 'code) read its parts. It answers a resource, usually a Parameters holding the outputs.

  • Checking is done for you. A request with a missing, misspelt, mistyped or out-of-range input is refused with status 400 and one issue per problem, before your handler runs. What the handler answers is held to #:out in the same way, so the OperationDefinition always tells the truth about the operation.

  • How it is called. With the inputs in the address (GET /$bmi?weight=80&height=180) or as a Parameters resource in a POST. An address holds text, which is read as the declared type. A Parameters resource names each value’s type (valueDecimal, valueCode), and a value under another type’s name is refused: "valueString": "80" for a decimal is a 400 that says to send valueDecimal.

An operation that already exists in the family is offered by naming it, with no handler: (operation $validate) after requiring it, or by reference, (operation "ValueSet/$expand"). That covers validation, the terminology operations (fhir-tx), StructureMap/$transform (fml) and Measure/$evaluate-measure (cql); each needs a require of the module that implements it.

5.4 Checking and serving🔗

The first line the server prints is its ready signal, and a script should wait for it. It names the address and the process number; stop the server with kill and that number (Ctrl-C when it runs in your terminal). A port already in use is one line saying so. After you edit the file, stop the server and start it again; the store keeps the data.

6 Strict and lenient search🔗

Suppose a client searches Patient?name=Lee on the first example’s server, which can search patients by gender and birth date only. FHIR allows two answers, and the choice matters more than it looks. A lenient server ignores the part it cannot apply and answers the rest. With nothing left to filter by, that is every patient; the Bundle carries a note saying name was ignored, which a careless client never reads. A strict server refuses, with status 400, and lists what it can search by:

$ curl 'http://localhost:43493/Patient?name=Lee'

{"resourceType":"OperationOutcome","issue":[{"severity":"error","code":"invalid","diagnostics":"search parameter `name` not supported here (strict search handling); this server searches with what /metadata advertises (Patient: gender, birthdate; every type: _id, _lastUpdated, _count, _offset, _sort)"}]}

Lenient is FHIR’s default and the default here; it suits a public reference server. For patient data, where a misspelt filter must never turn into "everyone’s records", declare (server #:search-handling "strict"). A client can also ask one lenient server to be strict for one request, with the header Prefer: handling=strict. The line search: that serve prints at start-up says which the server is. A server generated from a guide is lenient.

7 What happens on a write🔗

A create or update goes through the same steps in both kinds of server.

  • It is validated as sent. The resource is checked by the family’s validator (fhir-validation) against FHIR’s rules for its type and the profiles it claims. An error refuses it with status 422 and every issue; nothing is stored. A warning does not stop it, unless the server was declared with #:warnings "refuse". To see warnings without storing anything, send the resource to /Patient/$validate first.

  • It gets an id and a version. On a create (POST) the server chooses the id, ignoring one you sent; the Location header gives it. To choose the id yourself, declare update and send PUT /Patient/ann. Each write stamps meta.versionId and meta.lastUpdated, and the previous version is kept.

  • It is indexed for every search parameter of its type, in the same step as the write, so a search just after a write finds it.

  • Its references can be checked. With #:references "checked", an observation that names Patient/nope is refused when the server serves patients and holds none of that id. By default it is stored as sent.

8 Pages, versions and conditional requests🔗

These are FHIR’s own rules for talking to a server; every server here follows them.

A search can be asked for a page at a time. _count is the page size. The answer’s total is the number of resources that match, not the number on the page, and a next link leads to the following page (previous leads back). Here three patients match and two were asked for:

$ curl -s "http://localhost:8080/Patient?gender=female&_count=2"

{"resourceType":"Bundle","type":"searchset","total":3,

 "link":[{"relation":"self","url":"http://localhost:8080/Patient?gender=female&_count=2"},

         {"relation":"next","url":"http://localhost:8080/Patient?gender=female&_count=2&_offset=2"}],

 "entry":[ … two patients … ]}

Follow next until an answer has none. To get the number alone, ask for _summary=count: the answer has the total and no entries. A search may also be sent as POST /Patient/_search with the parameters as a form in the body, which keeps them out of the url.

Every answer that is one resource carries its version. The ETag header is the resource’s meta.versionId, and Last-Modified its meta.lastUpdated:

$ curl -s -i http://localhost:8080/Patient/d044f915

HTTP/1.1 200 OK

ETag: W/"1"

Last-Modified: Fri, 13 Nov 2026 20:39:31 GMT

A read can say which version you already have. Send that version back as If-None-Match (or the date as If-Modified-Since); if it is still the current one the server answers 304 and sends nothing:

$ curl -s -i http://localhost:8080/Patient/d044f915 -H 'If-None-Match: W/"1"'

HTTP/1.1 304 Not Modified

ETag: W/"1"

Content-Length: 0

A write can say which version it changes. Two people who read version 1 and both send an update would otherwise overwrite each other without knowing. With If-Match, an update, patch or delete is carried out only if the version named is still the current one:

$ curl -s -i -X PUT http://localhost:8080/Patient/d044f915 -H 'If-Match: W/"7"' …

HTTP/1.1 412 Precondition Failed

{"resourceType":"OperationOutcome","issue":[{"severity":"error","code":"conflict","diagnostics":"If-Match: W/\"7\", but the current version is W/\"1\": the resource has changed since you read it"}]}

Read the resource again, apply your change to what you get, and send it with the new version.

A deleted resource is gone, not unknown. Reading it answers 410 Gone and says where its earlier versions are; an id that was never used answers 404. (A server you declare can tell the two apart when it serves history-instance; without it both are 404.) The delete is a version of its own: the history lists it first, as a DELETE with no resource, reading that version answers 410 too, and a resource made again under the same id is the version after it (a create: 201).

A write can depend on a search. A create sent with If-None-Exist: identifier=urn:mrn|1 is made only when that search finds nothing; when it finds one resource, that resource is the answer (200) and nothing is written, so a client that retries a create makes no second copy. PUT /Patient?identifier=urn:mrn|1 updates the one patient the search finds, or creates it when there is none, and DELETE /Patient?identifier=urn:mrn|1 deletes the one it finds. A search that finds several is refused with 412 and nothing is written, and a parameter the server does not search on is a 400: ignored, it would let the write fall on resources the criteria do not name.

9 The store🔗

Both kinds of server keep their data in one SQLite file. SQLite is a database that lives in a single file and needs no separate program; you can copy the file, back it up, or open it with any SQLite tool. Inside, each resource is kept as its JSON, with every earlier version and the search indexes. Two files with the same name plus -wal and -shm may sit beside it while a server is running or after it was stopped abruptly; they are part of the store and are read again at the next open.

9.1 Loading files🔗

raco fhir-server load fills a store from files, with no server running: FHIR resources as JSON, Bundles (each entry is stored), bulk-data files (.ndjson or .ndjson.gz: one resource to a line, read a batch at a time, so a file of any size loads), and .cql libraries (stored as Library resources). Here data/ holds a patient and one of her lab results:

$ raco fhir-server load clinic.db data/

a1c.json: 1 resource(s)

ann.json: 1 resource(s)

loaded 2 resources into clinic.db (indexed for FHIR 4.0.1 search)

A resource with an id keeps it, and loading the same file again replaces it with a new version. The resources are indexed for every search FHIR defines for their type, in FHIR R4 unless you say --fhir-version 5.0.0 or 6.0.0 (a server you declare is R6), so a server started over the store later finds them.

By itself load checks nothing: it stores what it reads. Add --validate to have every resource, a Bundle’s entries included, held to its type and to the profiles it claims before anything is written. Each problem is printed with its file, and one error means nothing is loaded:

$ raco fhir-server load clinic.db incoming/ --validate

bea.json: Patient/bea: error: Patient.gender: code `femme` not in required value set http://hl7.org/fhir/ValueSet/administrative-gender; it holds female, male, other, unknown

bea.json: Patient/bea: error: Patient.birthDate: '1980-02-30' is not a valid date (February 1980 has 29 days)

fhir-server load: 1 of 2 resource(s) are not valid FHIR 4.0.1 (2 error(s)): nothing was loaded

The command exits with status 1 and makes no store. Warnings are printed and do not stop the load. When the data claims a guide’s profiles, name the guide with --package hl7.fhir.us.core (or a .tgz file; repeatable), as for raco fhir-validate: without it a claimed profile that nothing in context defines is a warning, and the resource is checked against its base type alone.

9.2 Large files🔗

A bulk export is one resource to a line (.ndjson, often gzipped), a file to a type, and can hold hundreds of thousands of resources. load reads such files as a stream and spreads the work over every core of the machine: worker processes read the lines, stamp the resources and work out their search index entries, and one process writes. When the store is empty, the search indexes are built once at the end instead of entry by entry. The hospital dataset this is measured on (a public intensive-care dataset of 928,935 resources, most of them observations) loads in a little over three minutes on four cores, about 4,700 resources a second. What is stored is exactly what loading the resources one by one stores.

9.3 Indexing again🔗

A resource is indexed for search when it is written. When the way values are indexed changes (a newer version of this package, a store loaded as another FHIR version), the resources already stored keep their old index entries. raco fhir-server reindex works them out again:

$ raco fhir-server reindex clinic.db

indexed 2 resources of clinic.db again (for FHIR 4.0.1 search)

It happens in one transaction: a reindex that is interrupted leaves the store as it was. A store made before periods (an encounter’s, a procedure’s) were indexed as dates needs it once: until then a search by such a date finds nothing in it.

--param <name> indexes the named search parameters only and --kind date every parameter of one kind, which takes less time and disk on a large store. A store made before dates were also kept as their records wrote them answers a date without a zone by UTC days until raco fhir-server reindex <store.db> --kind date has run.

9.4 Reading it with SQL🔗

raco fhir-server sql runs one SQL query over a store and prints the rows as CSV. It only reads: anything but a SELECT is refused. Each stored type is a table of that name with the columns id, versionId, lastUpdated and resource, the JSON. SQLite’s ->> takes a value out of the JSON by its path:

$ raco fhir-server sql clinic.db "SELECT id, resource ->> '$.subject.reference' AS patient, resource ->> '$.valueQuantity.value' AS value, resource ->> '$.valueQuantity.unit' AS unit FROM Observation"

id,patient,value,unit

a1c-1,Patient/ann,7.2,%

Two more tables span the types: resources (every current resource, with a type column) and history (every version ever written, the same columns):

$ raco fhir-server sql clinic.db "SELECT type, count(*) AS n FROM resources GROUP BY type"

type,n

Observation,1

Patient,1

This is the quick look. For tables you will ask for again, describe them once as SQL on FHIR views, which name their columns by FHIRPath rather than by JSON paths.

10 Measures🔗

A quality measure counts, among a group of patients, how many received some recommended care: of the women in the age range for breast-cancer screening, how many had a mammogram recently enough. FHIR writes one as a Measure resource that points to a library of logic in Clinical Quality Language (CQL). The operation $evaluate-measure runs it and answers a MeasureReport with the counts.

A store that holds the Measure, its libraries, the value sets they use and the patients’ records is all that is needed. Here the files are the breast-cancer-screening measure and two of its test patients from the public eCQM content (in the cql repository, under tests/vendor/ecqm):

$ raco fhir-server load measures.db ecqm/cql

…

loaded 12 resources into measures.db (indexed for FHIR 4.0.1 search)

$ raco fhir-server load measures.db ecqm/measure

…

loaded 4 resources into measures.db (indexed for FHIR 4.0.1 search)

$ raco fhir-server load measures.db ecqm/valueset

…

loaded 57 resources into measures.db (indexed for FHIR 4.0.1 search)

$ raco fhir-server load measures.db ecqm/tests/BreastCancerScreeningsFHIR/denom-EXM125

$ raco fhir-server load measures.db ecqm/tests/BreastCancerScreeningsFHIR/numer-EXM125-diagnosticReport

Then evaluate. The measure is named by its id or its canonical url, and the period is given as two dates:

$ raco fhir-server evaluate-measure measures.db BreastCancerScreeningsFHIR \

  {"code":{"coding":[{"code":"initial-population", …}]},"count":2},

  {"code":{"coding":[{"code":"denominator", …}]},"count":2},

  {"code":{"coding":[{"code":"denominator-exclusion", …}]},"count":0},

 "measure":"http://ecqi.healthit.gov/ecqms/Measure/BreastCancerScreeningsFHIR",

Read the populations: both patients are in the initial population and the denominator (they are eligible), one is in the numerator (she had the screening), and the score is one half. 11.2 A declared server, in process🔗

A declaration file is a module. It provides app (the server as a value), capability-statement and operation-definitions, and each operation you declared as a function. Nothing needs to listen on a port for you to use them:

(require (only-in fhir/capability/runtime dispatch search-request)
         (only-in "study.capability.rkt" app $double))
(dispatch app (search-request 'Patient '((gender . "male"))))   ; a searchset Bundle
($double #:x 2.5)                                               ; a Parameters: doubled = 5.0

11.3 Operations alone, over HTTP🔗

Any of the family’s operations can be served with no resources at all. The CapabilityStatement is derived from the list:

(require fhir/capability/operations fhir/conformance/operations fhir/terminology/operations
         fhir/r5/schemas)
(define stop (serve-operations (cons $validate terminology-operations) #:port 8080
                               #:terminology-capabilities (current-terminology-capabilities)))

That is what raco fhir-tx serve does for the terminology operations.

11.4 The store directly🔗

The store is usable without any server: versioned writes, history, search, and FHIR transaction Bundles. Search is driven by a catalog of search parameters read from a package.

(require fhir/store/fhir-sqlite fhir/store/fhir-engine fhir/store/bundle fhir/store/serve
         fhir/store/ig-params fhir/spec-package fhir/r5/schemas)
(define store (open-fhir-store "fhir.db"))
(define core (spec-package-path "hl7.fhir.r5.core.tgz"))
(define catalog (search-params-from-package core))
 
(define-values (type id version) (fhir-create! store patient #:search-params catalog))
(fhir-search store "Patient" '(("gender" . "male")) #:search-params catalog)
(fhir-update! store (hash-set patient 'id id) #:search-params catalog)   ; => 2, the new version
(fhir-history store "Patient" id)                                        ; both versions
(process-bundle! store transaction-bundle #:search-params catalog)       ; all of it, or none
 
; a server over the store: the types you name, searched by the package's parameters;
; with audit, every write also records an AuditEvent and a Provenance
(serve-app (make-store-app store #:package core #:types '(Patient Observation) #:audit? #t) #:port 8080)

13 Limits🔗

What a FHIR server can be asked for and these do not do. A server generated from a guide reports the search parameters, includes, interactions and operations it cannot do as gaps; the rest is not reported anywhere but here.

  • Not for production. There is no TLS, and no access control beyond one fixed token (--bearer): no SMART on FHIR, OAuth, scopes or per-patient permissions. A guide’s security section is copied into /metadata unchanged. Run these servers on your own machine or a trusted network.

  • Search that is not done. Reverse chaining (_has), a chain of more than one step (one step is done: patient.name=…, medication.code=…), composite and special parameters, _summary, _elements, _total, _filter, _text, _content, :iterate, the modifiers :above, :below, :in and :identifier, and searching across all types at once. Of _summary only count is done. A lenient server answers as if the unsupported part were not there (Strict and lenient search). Quantity search does not convert units. String search covers names and addresses, not every complex type.

  • Paging. Pages are taken by position (_offset): a resource written between two requests can shift what the next page holds. There are next and previous links, no first or last. A history is not paged.

  • raco fhir-server load validates only when asked. Without --validate it stores and indexes what it reads.

  • Conditional writes (If-None-Exist, PUT /Type?param, DELETE /Type?param) act on one match at most: a search that finds several is refused (412), and a conditional delete never deletes several. If-Match and a conditional write’s search are checked just before the write, not in one step with it: two writers a few milliseconds apart can both pass.

  • History. Of one resource and of one type, with _since and _count; not of the whole server, no _at, no paging.

  • Transactions. A server generated from a guide (and make-store-app) accepts transaction and batch Bundles at POST /: a transaction is all or nothing, and temporary urn: references between its entries are resolved. Its entries may be POST, PUT and DELETE; no GET or PATCH entries, and no conditional ones. On a generated server each resource in a Bundle is validated as a single write is: a transaction with an invalid entry is refused whole, and a batch answers that entry with its problems (422) and writes the others. A declared server has no transaction endpoint.

  • PATCH takes JSON Patch only, not FHIRPath Patch.

  • Transport. JSON only, no XML and no content negotiation. HTTP/1.1, one request per connection; no HEAD or OPTIONS, no CORS headers.

  • Operations. Those implemented in the family (validation, terminology, snapshot, transform, measure evaluation, US Core’s $docref) and the ones you declare. No $everything or patient compartments, no subscriptions, bulk export or GraphQL.

  • FHIR versions. A declared server is R6 and cannot be made R4 or R5; an R4 client’s JSON is accepted where the two versions agree (the capability guide lists where they differ). A generated server has its guide’s version.

  • A generated server’s CapabilityStatement keeps some of the guide’s flags as written (conditionalCreate, conditionalUpdate, versioning, updateCreate) as written, and always lists transaction and batch.

  • Measures. Proportion measures counted per patient; see the limits of cql.

14 Words used here🔗

  • Resource: one FHIR document, such as a Patient or an Observation, written as JSON.

  • FHIR server: a program that stores resources and answers requests for them over HTTP, in the way FHIR lays down (its REST API).

  • Interaction: one of the things a server lets you do with a resource: read, create, update, delete, search, and the others in A server you declare.

  • Search parameter: a named thing a resource can be searched by (gender, birthdate); its kind (token, string, date, reference …) decides how values are compared.

  • CapabilityStatement: a server’s own description of what it supports, served at /metadata.

  • Operation: a named service beyond the interactions, written with a dollar sign ($validate, $evaluate-measure). OperationDefinition: its formal description.

  • Parameters: the FHIR resource that carries an operation’s named inputs or outputs.

  • Bundle: FHIR’s envelope for several resources: a search result (searchset), a history, or a transaction, a set of writes done all together or not at all.

  • OperationOutcome: the FHIR resource that reports problems, one issue each.

  • Implementation Guide (IG): a published set of profiles, search parameters, operations and examples for one purpose. Package: the .tgz file it is distributed as.

  • Profile: stricter rules for one type of resource in one setting. A resource claims a profile by listing it in meta.profile.

  • Gap: something a guide asks of a server that this one does not do.

  • Strict, lenient: whether a search with a parameter the server cannot apply is refused or answered without it.

  • Store: the SQLite file the resources, their versions and the search indexes are kept in.

  • Measure: a quality measure. Population: one of its counted groups (initial population, denominator, numerator). MeasureReport: the result.

  • Handler: the function that does an operation’s work.

  • Canonical url: the web address that names a profile, a measure or an operation’s definition. It is a name; nothing needs to be served there.

15 How it is tested🔗

Against published guides, used as the specification of a server:

  • US Core 9.0.0. The generated server serves all 31 resource types with no unmet requirement at any level; the guide’s examples load through validation with none rejected; and each example is found by searching on its own values, 2468 searches out of 2468.

  • mCODE 4.0.0, compiled from its FHIR Shorthand source, packed and served here: all 283 examples validate against its profiles, with no unmet requirement.

  • CQF Measures 5.0.0. A measure server generated from the guide evaluates two published measures for 65 test patients; 60 reports are as expected, and the 5 that differ are named in the test with the reason.

  • A declared server’s own description is valid FHIR: the derived CapabilityStatement, every OperationDefinition and a search result are run through the validator. The examples of the capability guide are run as written, over a real socket.

Speed is measured on one dataset, the same way each time (fhir-server/bench/store-bench.rkt): a public intensive-care dataset of 928,935 resources. It loads in a little over three minutes, and a search for one patient’s ten most recent observations among them answers in under a fifth of a second.

The repository’s TESTING.md has every suite, names the misses, and has the timings.

#lang fhir/capability🔗

 #lang fhir/capability package: fhir

The server, resource and operation forms, as in A server you declare; provides app, capability-statement and operation-definitions. The forms are checked when the module compiles (resource types, interactions, parameter types, server options) and every mistake is reported, each at its form. Everything from fhir/capability/runtime, fhir/capability/derive and fhir/r6/types is in scope. An inline (operation $code … #:handler h) also defines $code as a fhir/operation value (declared-operation): the same handler, applied in-process with the inputs and an in-process request, registered by its canonical (urn:fhir-capability:operation:<code>) and provided by the module — a pipeline declared once is served and callable (($code #:name value), (apply-operation "$code" …)).

  • (server #:store f #:search-handling s #:references r #:warnings w #:url u #:name n #:description d #:status s #:date d #:mode m #:format f ...), once; every keyword optional, each value a string. #:fhir-version is accepted only as the server’s own (R6).

  • (resource Type #:interactions (...) #:search-params ([name type] [name type "FHIRPath"] ...) #:repository r #:profile url). Without #:repository the resource is kept in the store: the one current-repository-factory gives (raco fhir-server serve --store, a workspace), else the server form’s #:store file, else a temporary SQLite file.
