fhir: a toolkit for AI agents on FHIR🔗

FHIR is the standard most health systems use to exchange data: a patient, a lab result, a prescription are each a small document called a resource. The standard also defines several small languages for working with those resources. This project implements them all, with a validator, a terminology service, a store and servers around them, built so that an AI agent can do real work with health data and you can check what it did: the agent writes a file in one of the languages, a tool checks it and says exactly where any mistake is, and then it runs over real data.

You do not need to know Racket (the language this is written in) to use it. Each language has a command-line tool, and there is one server, fhir-mcp, that an agent works through. Everything here works for a person at a terminal too.

1 Why it suits an agent🔗

An agent pays for every word it reads and writes, makes fewer mistakes the less it has to write, and needs to be told plainly when it is wrong. Four choices follow from that.

  • Languages, not JSON. A FHIR resource is JSON, and the definitions FHIR works with (a profile, a value set, a map, a library of logic) are long JSON documents. Each of FHIR’s languages is a shorter way to say one of them, and the tools compile the language to the JSON. So the agent reads and writes the language. Counted in a model’s own tokens over published material: a CQL library is 13% of the JSON it compiles to, a value set written in VCL 28%, a map 52%.

  • Say only what changes. A stored resource is changed by the rules that change it, not by sending the whole resource back: 26 tokens in a test of sixty changes where the resource as JSON was 535, with the same result every time.

  • The data as tables. A patient’s facts are spread over many resources, and most questions are about a table: the latest result per patient, the stays of a year. The agent defines the tables once over the stored data (a SQL on FHIR view for each kind of resource, a .sql file for a join) and a question is then one SQL statement. A table can keep, in a column, the resource each row came from, so an answer can still be traced to the record. The fhir-mcp page shows one.

  • Checked before it is written, traced after. Nothing reaches the data without being validated against FHIR and against your own rules, and every write records who made it, when, why and from which line of which text. A mistake comes back as one line, at its place, saying what was found and what would fix it.

Measured with Claude Sonnet on two benchmarks other people published, graded by their own graders, against the same data served as plain FHIR REST calls. On MedAgentBench (300 clinical tasks): 300 right at 6 thousand tokens a task, where an agent making REST calls got 294 right at 38 thousand. On FHIR-AgentBench (questions about a hospital’s records): 147 of 150 right at 10 thousand tokens a question, against 109 at 69 thousand; over its whole test split of 409 questions, asked three times, 402 are marked right each time, and every question whose recorded answer can be held to is right every time.

How those numbers were reached says what matters. Through the workspace’s nine tools from a shell, the same agent got 300 of MedAgentBench’s tasks right at 41 thousand tokens and 122 of the 150 questions at 57 thousand: more right answers than REST, for tokens of the same order. The tokens went when the agent was given the few actions a task needs as the tools of one process, and a prompt holding only what its first step uses. The answers came when the benchmark’s own relational schema was defined over the FHIR store by an agent, as views, and its questions were answered in SQL beside an example query of the same kind from the benchmark’s training questions (the REST agents, run in an earlier round, had the data alone).

What those numbers do not show is that the tools alone beat REST. Tested on its own (one harness, the data alone, 150 questions neither side had been run on, the protocol written before the run) the workspace’s reading tools and a plain REST server with Python are level: 125 and 126 right, at 25 and 30 thousand tokens a question. The difference above comes from the tables defined over the store, given with examples from the benchmark’s training questions; which of the two carries it has not been separated. The protocol and the result are in fhir-examples.

Where a language does show is in what is built from it. Four published quality measures were implemented by independent agents, five from each measure’s English narrative and five from its CQL (its formal specification), and held to the authors’ test cases: 93% right from the narrative, 98% from the CQL, 99% with the CQL run by the engine; the implementers agree with each other on 88% of cases from the narrative and 96% from the CQL. The English left open what the specification states: which encounters count as "a visit", whether a diagnosis "during" a period must start in it. Four measures and one model, so a result to repeat, in the same place.

Where a declaration did not show: three operations were built as servers by independent agents, five declared in the capability language and five by hand in Python each, kept up through three changes to the operation’s definition, and held to requests written by an agent that had not seen the toolkit. The hand-built servers answered every request as the definition says; the declared ones 94%, at two and a half times the tokens. Every miss was one leniency of the framework (a value sent under another type’s key was converted), since fixed; with it fixed the same servers are level. An agent writes those checks by hand correctly, so there the declaration is no advantage to it.

And asked to write 24 published profiles from their stated requirements, a model got 1427 of 1431 constraints right in FHIR Shorthand at half the tokens of the JSON. The harnesses, the runs and every miss are in fhir-examples.

A correction, as an agent makes it (the first file was written when the reading was stored):

$ cat fix.fsh

Instance: Observation/a1c-1

* status = #amended

* valueQuantity = 9.1 '%'

* note.text = "repeat sample"

$ raco fhir-mcp call stage fsh=@fix.fsh

{"changes":[{"action":"update","changed":["note: added [{\"text\":\"repeat sample\"}]","status: \"final\" → \"amended\"","valueQuantity.value: 9.4 → 9.1"],"resource":"Observation/a1c-1"}],"errors":0,"next":"commit stage=stage-2 writes the 1 change(s) to the store fhir.db","stage":"stage-2"}

$ raco fhir-mcp call commit stage=latest reason="repeat sample" agent=Practitioner/dr-ng

$ raco fhir-mcp call describe ref=Observation/a1c-1/_history as=csv columns=versionId,agent,reason,value,at

versionId,agent,reason,value,at

2,Practitioner/dr-ng,repeat sample,9.1 %,fix.fsh:4

1,Practitioner/dr-ng,clinic intake,9.4 %,readings.fsh:15

The first line of the file names the stored resource; the lines under it are what changes. The answer to stage says what would change and that nothing is wrong; commit writes it; the last command reads the resource’s history back as a table. The fhir-mcp page starts from an empty folder.

3 In Racket, and in Python🔗

The toolkit is written in Racket, and it is a set of Racket packages before it is anything else: the command-line tools, the agent’s workspace and the Python package are built from them. Each language is a #lang, so a .fsh, .cql, .map, .vcl or .sof file is a module that is checked when it compiles and that a program requires like any other; beside them are the libraries (fhirpath/eval, cql/run, fhir/operation) and a raco command for each language. A profile, a map and a library of logic, used by one program:

#lang racket/base

(require json

         (only-in "fsh/intake.fsh" canonical-of)     ; a profile, in FHIR Shorthand

         (only-in "qr2patient.map" transform)        ; a map, in the FHIR Mapping Language

         (only-in "Intake.cql" evaluate)             ; clinical logic, in CQL

         (only-in cql/value render))

 

(define answers (call-with-input-file "qr.json" read-json))

(define patient (transform answers #:validate (canonical-of "IntakePatient")))

(printf "~a, 65 or older: ~a\n"

        (hash-ref (car (hash-ref patient 'name)) 'text)

        (render (evaluate (list patient) #:define "Is 65 Or Older")))

$ racket main.rkt

Ana Rivera, 65 or older: true

A mistake in one of those files stops the build, at its line:

qr2patient.map:14:49: fml check error: `gendr` is not an element of Patient (did you mean `gender`?)

raco fhir new pipeline my-pipeline writes that project (the profile, the map, the library, a form’s answers and a test), and raco fhir guide racket is the Racket route on one page.

From Python it is one package, agentfhir, with nothing else to install. Beside the Python libraries people use for FHIR today, each measured by a program you can run:

  • More of the standard. Of the 934 expressions in HL7’s FHIRPath test suite it answers 932 as the suite requires; fhirpathpy answers 788. And where a Python library does one thing (FHIRPath, or a class for each resource), this is FHIRPath, validation against an implementation guide’s profiles, terminology, FHIR Shorthand, CQL, the mapping language, SQL on FHIR, search and a store. The usual tools for the rest are Java and Node programs.

  • Checks that catch what a validator catches. Eight kinds of mistake planted in a published example: it refuses all eight, as HL7’s validator does; fhir.resources, which checks a resource’s shape, refuses three.

  • Quick where there is work to do. US Core’s 230 published examples against the guide’s profiles: 2.1 s, where HL7’s Java validator run as a process takes 49 s. One expression over 5,000 Patients in one call: 55 ms, where a fhirpathpy loop takes 194 ms. For one small question of one small resource a pure-Python library is quicker (0.04 ms against 0.10 ms): nothing crosses between two processes there.

4 Install🔗

There are no downloads yet, so you build the tools once. You need Racket 9 to build them; the result runs without Racket on any machine of the same kind.

for r in fhir fhirpath vcl cql fml fsh sql-on-fhir; do

  git clone https://github.com/oloveluck/$r.git

done

raco pkg install --link --auto --batch --no-docs \

  fhir/fhir fhir/fhir-spec fhirpath vcl fhir/fhir-tx fhir/fhir-validation \

  cql fml fsh fhir/fhir-server fhir/fhir-lsp fhir/fhir-mcp sql-on-fhir

fhir/build-tools.sh dist

export PATH="$PWD/dist/bin:$PATH"

The first two commands fetch the source and install it as Racket packages; after them every tool already works as raco <tool> (raco fsh, raco cql, …). build-tools.sh builds the standalone tools (fsh, cql, …) into dist/, about 380 MB with the HL7 packages they read. The two forms take the same arguments; these pages write raco <tool>. fhir/tools-smoke-test.sh dist then asks each of the twelve for one piece of real work, with nothing but the tools on the path, and prints a line for each.

fhir-server needs the system’s SQLite library. A tool also looks for FHIR packages in the directories named by the environment variable FHIR_PACKAGE_PATH.

5 First steps🔗

Pick the one closest to what you came for. Each is a few lines and takes a few minutes.

  • Check a resource. raco fhir-validate patient.json reads a FHIR resource and lists what is wrong with it: a code that is not allowed, a date that is not a date, a required field left out. See fhir-validation.

  • Write a rule for your data. A profile says what a valid resource looks like in your setting ("every lab result names its patient"). You write it in FHIR Shorthand, with an example, and raco fsh check tells you whether the example passes, pointing at the line that does not. Start with the fsh quick start.

  • Ask a question of patient data. A CQL library such as "who has had an HbA1c test, and was the latest above 9 %?" runs over a folder of patient resources. See cql.

  • Run a server. raco fhir-server serve-ig hl7.fhir.us.core starts a FHIR server that follows a published Implementation Guide: it accepts the resources the guide describes, refuses invalid ones and answers the searches the guide requires. See fhir-server.

  • Work through an AI agent. raco fhir-mcp init my-workspace makes a folder that Claude (or another agent) can work in: it writes the languages, checks them, stores data and answers questions, and every change it makes is recorded with who, when and why. See fhir-mcp.

  • See it all together. fhir-examples/screening is one small program written in seven of the languages, from an intake form to a screening result. See fhir-examples.

6 How the pieces fit🔗

  • Everything is a FHIR resource. A profile, a value set, a map, a library of logic are themselves FHIR resources; each language is a shorter way to write one. So what one language produces another can use: a profile written in FHIR Shorthand checks the patient a map produced; a CQL library reads the same records a SQL on FHIR view turns into a table.

  • Things find each other by address. Every definition has a web address (its canonical url). When one file refers to a value set or a profile by that address, the tools find it, whether it is in another of your files, in a published package or in a store.

  • Mistakes are reported where they are. Every tool reports a problem as file:line:column, with the line and a marker under the place. The same report is available as JSON or as a FHIR OperationOutcome (--format json|outcome), so an editor or an agent can read it too.

  • FHIR’s operations are ordinary functions. FHIR names its services with a dollar sign: $validate, $expand, $transform, $evaluate-measure. Here each is a function you can call from a program, and the same function is what the server answers with over HTTP.

  • For programmers: each file is a module. In Racket, a file in one of the languages can be required like any other module: (require "profile.fsh") gives its compiled resources, (require "screening.cql") a function over a patient’s data. A mistake in the file stops the build, at its line. The fhir page has the details.

7 The packages in this repository🔗

Each language lives in a repository of its own (the links in the table above). This repository holds what they share and the tools around them.

  • fhir: the foundation. FHIR resources read, checked and written as JSON, for FHIR versions R4, R5 and R6; the machinery the other packages build on. raco fhir.

  • fhir-spec: the HL7 packages the tools read (the FHIR specification itself and the Implementation Guides the tests use). Data only.

  • fhir-validation: the validator. raco fhir-validate.

  • fhir-tx: the terminology service: which codes a value set holds, whether a code is in it, what a code means. raco fhir-tx.

  • fhir-server: FHIR servers, generated from an Implementation Guide or declared in a short file, over a SQLite store. raco fhir-server.

  • fhir-lsp: a language server, so an editor underlines mistakes in the five text languages as you type. raco fhir-lsp.

  • fhir-mcp: the workspace an AI agent works in. raco fhir-mcp.

  • fhir-api: the toolkit from Python (the agentfhir package) and from any other language: its functions over one small protocol. raco fhir-api.

8 Words used here🔗

  • Resource: one FHIR document, such as a Patient or an Observation, written as JSON.

  • Profile: a set of rules a resource must follow in some setting, on top of FHIR’s own (a StructureDefinition resource).

  • Implementation Guide (IG): a published set of profiles, value sets and examples for one purpose, such as US Core or the International Patient Summary. It is distributed as a package, a .tgz file.

  • Value set: a named set of codes, such as "the codes that mean a blood-pressure reading". A code system is where the codes come from (LOINC, SNOMED CT).

  • Canonical url: the web address that names a definition, such as http://hl7.org/fhir/ValueSet/administrative-gender. It is a name; nothing needs to be served there.

  • Operation: a named service FHIR defines, written with a dollar sign ($validate).

  • Terminology: everything to do with codes: value sets, code systems, and the maps between them.

9 Limits🔗

Each page ends with a list of what its package does not do. The largest across the project:

  • FHIR is read and written as JSON only, never XML.

  • The server does not do conditional create, update or delete by a search, or SMART authorization.

  • The validator does not follow references to check what they point at.

  • The terminology service only knows the code systems in the packages it is given. SNOMED CT and LOINC are not shipped, so a value set defined by a rule over them cannot be listed out, though a value set that lists its codes works.

  • CQL computes proportion measures for FHIR Measure resources; the other kinds of scoring are available for measures in the cqm-models format.

  • The mapping language runs every transform but dateOp.

  • FHIR Shorthand reproduces most, not all, of what the reference compiler (SUSHI) writes for the published guides it is tested on; TESTING.md in each repository has the numbers.
