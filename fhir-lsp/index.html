9.3

fhir-lsp: a language server for the FHIR languages🔗

When you write a file in one of FHIR’s languages, you want to know about a mistake while you are still on the line: a misspelt element, a function that does not exist, a bracket never closed. An editor cannot tell you by itself, because it does not know the language.

A language server is the piece that does. It is a program your editor starts in the background and sends your text to as you type. The server answers with the problems it finds and where they are, and the editor underlines them. The editor can also ask it what a name means, where a name is defined, and what could be typed next. Editors and servers speak a common protocol, the Language Server Protocol, so one server works in any editor that speaks it.

This package is that server for five languages:

language

  

files

  

what it is for

FHIR Shorthand

  

.fsh

  

profiles, value sets and examples

Clinical Quality Language (CQL)

  

.cql

  

logic over a patient's record

FHIR Mapping Language

  

.fml, .map

  

converting data from one shape to another

ValueSet Compose Language (VCL)

  

.vcl

  

a set of codes in one line

FHIRPath

  

.fhirpath

  

a question asked of one resource

The problems it reports are the ones each language’s own command-line tool reports, word for word.

Part of the fhir family of FHIR languages and tools.

1 What you can do with it🔗

  • See mistakes as you type, underlined at the place, with the message the command line would print. Every language.

  • See a file’s outline: its profiles and instances, its definitions, its groups. FHIR Shorthand, CQL and the mapping language.

  • Hover over a name to see what it is: an element’s cardinality and description, a definition’s text. FHIR Shorthand, CQL and the mapping language.

  • Jump to where a name is defined, in this file or another one of the project. FHIR Shorthand, CQL and the mapping language.

  • Complete what you are typing: keywords, the names your project defines, the elements of a type. FHIR Shorthand, CQL and the mapping language.

  • Check files without an editor: raco fhir-lsp check prints what the server would show (Checking files without an editor).

What each language gets says exactly what each language gets.

2 Setting it up🔗

Three steps: install the tools, tell your editor about the server, open a file.

2.1 1. Install🔗

Install the tools as the family’s front page describes. Then ask the server what it serves:

$ raco fhir-lsp languages

fsh .fsh

cql .cql

fml .fml .map

vcl .vcl

fhirpath .fhirpath

If you see these five lines, the server is installed. The command an editor must start is raco fhir-lsp, with nothing after it. (If you built the standalone tools, it is fhir-lsp.) It talks to the editor over its standard input and output, which is what editors expect by default.

2.2 2. Tell your editor🔗

An editor needs to know two things: which files are in these languages, and which command to start for them. The server works out the language from the file’s extension, so the name your editor gives a language does not matter.

Neovim (0.10 or newer). Put this in init.lua:

vim.filetype.add({ extension = {

  fsh = "fsh", cql = "cql", fml = "fml", map = "fml", vcl = "vcl", fhirpath = "fhirpath" } })

vim.api.nvim_create_autocmd("FileType", {

  pattern = { "fsh", "cql", "fml", "vcl", "fhirpath" },

  callback = function()

    vim.lsp.start({

      name = "fhir-lsp",

      cmd = { "raco", "fhir-lsp" },

      root_dir = vim.fs.root(0, { "sushi-config.yaml", ".git" }),

    })

  end,

})

The first statement names the file types; the second starts the server whenever a file of one of them is opened.

Emacs (29 or newer, which includes the client eglot). Put this in your init file:

(define-derived-mode fsh-mode prog-mode "FSH")

(define-derived-mode cql-mode prog-mode "CQL")

(define-derived-mode fml-mode prog-mode "FML")

(define-derived-mode vcl-mode prog-mode "VCL")

(define-derived-mode fhirpath-mode prog-mode "FHIRPath")

(add-to-list 'auto-mode-alist '("\\.fsh\\'" . fsh-mode))

(add-to-list 'auto-mode-alist '("\\.cql\\'" . cql-mode))

(add-to-list 'auto-mode-alist '("\\.\\(fml\\|map\\)\\'" . fml-mode))

(add-to-list 'auto-mode-alist '("\\.vcl\\'" . vcl-mode))

(add-to-list 'auto-mode-alist '("\\.fhirpath\\'" . fhirpath-mode))

(with-eval-after-load 'eglot

  (add-to-list 'eglot-server-programs

               '((fsh-mode cql-mode fml-mode vcl-mode fhirpath-mode) . ("raco" "fhir-lsp"))))

(dolist (hook '(fsh-mode-hook cql-mode-hook fml-mode-hook vcl-mode-hook fhirpath-mode-hook))

  (add-hook hook #'eglot-ensure))

The first lines give each language a mode and tie it to its file extensions. The rest tells eglot which command serves those modes, and to start it when such a file is opened. If you already have a mode for one of the languages, keep it and name it in the list instead.

VS Code. VS Code talks to a language server through an extension, and there is no extension made for this server yet. A general-purpose client extension does the job (one is called Generic LSP Client). Whichever you choose, give it:

  • the command raco with the one argument fhir-lsp (or the standalone fhir-lsp, if the extension takes a single program);

  • the files it applies to: .fsh, .cql, .fml, .map, .vcl and .fhirpath;

  • standard input and output as the way to talk to it, which is usually the default.

Some client extensions run only one server for one language at a time. With those, set it up for the language you write most.

Any other editor that speaks the protocol (Helix, Zed, Sublime Text, Kate …) needs the same three facts.

2.3 3. Open a file🔗

Save this as bp.fsh and open it. It is a profile for blood-pressure readings with one misspelt element:

Profile: BloodPressure

Parent: Observation

Id: blood-pressure

* subject 1..1

* efective[x] 1..1

After a moment efective[x] is underlined, and the message reads:

profile: BloodPressure: `efective` is not an element of Observation (did you mean `effective`?)

(Emacs shows where the message comes from before it: fsh compile: profile: BloodPressure: ….) Correct the spelling and the underline goes away. Put the cursor on subject and ask for hover (the mouse in VS Code, K in Neovim, M-x eldoc in Emacs) to see what FHIR says that element is.

3 When nothing happens🔗

Work down this list. Each step rules out one cause.

  1. Is the server installed? Run raco fhir-lsp languages in a terminal. It should print the five lines shown above.

  2. Does the server see the mistake? Run it on the file, with no editor involved:

    $ raco fhir-lsp check bp.fsh

    bp.fsh:5:3: fsh compile error: profile: BloodPressure: `efective` is not an element of Observation (did you mean `effective`?)

     5 | * efective[x] 1..1

       |   ^^^^^^^^^^^

    If this prints the problem, the server is fine and the editor is not reaching it. If it prints nothing, the server finds nothing wrong with the file.

  3. Can the editor find the command? An editor started from a desktop icon may not have the same PATH as your terminal. Give it the full path to raco (the terminal command which raco prints it), or start the editor from the terminal.

  4. Did the editor start the server for this file? The file’s name must end in one of the extensions above. In Neovim, :lua print(#vim.lsp.get_clients({ bufnr = 0 })) prints 1 when a server is attached to the file you are in. In Emacs, M-x eglot starts the server by hand and says what went wrong if it cannot; M-x eglot-events-buffer shows the conversation. In VS Code, the Output panel has an entry for the client extension.

  5. Is the language installed? The server loads each language when a file of its kind is first opened. If that language’s package is missing, the file gets one message saying so (the fsh package is not installed) and the other languages keep working.

  6. Give it a moment. The first check of a FHIR Shorthand file reads FHIR’s definitions, which takes a couple of seconds. Later checks are quicker.

4 What each language gets🔗

Every language gets its problems reported. Three of them get the rest.

language

  

problems reported as you type

  

outline, hover, definition, completion

FHIR Shorthand

  

what compiling the project finds: text that does not parse, an element the type does not have (at its rule), a Parent, InstanceOf or RuleSet that no file of the project and none of its packages defines

  

yes, across the project's files

CQL

  

text that does not parse; every definition translated, each failure at its place, with warnings

  

yes; into included libraries beside the file

Mapping language

  

text that does not parse; the map checked against the structures it names: an element the type lacks, a value that cannot go into its element, a wrong call to a group, a required element never written

  

yes; into imported maps beside the file

VCL

  

the expression parsed and turned into a value set definition

  

no

FHIRPath

  

the expression parsed

  

no

4.1 FHIR Shorthand🔗

A file is compiled together with the other .fsh files of its project, so a profile in one file can be the Parent of a profile in another. The project is the folder that holds the nearest sushi-config.yaml (beside the file, or up to two folders above), and that file gives the project’s address, its FHIR version and the packages it depends on. Without one, the project is the file’s own folder and FHIR R5 is assumed. A problem in another file of the project is reported on that file.

  • Hover on a rule’s element path shows what the base type says about that element: its path, how many values it may have, its types, its short description and definition. The base is the file’s Parent or InstanceOf, followed through the project’s own profiles and aliases. Hover on a name shows the declaration it refers to.

  • Go to definition on a name opens its declaration, in whichever file of the project has it: a Parent, an InstanceOf, a value set in a binding, an alias, a RuleSet in an insert, an invariant, an instance in a Reference. A name is found by name, by id or by its address.

  • Completion. At the start of a line: the keywords that begin an entity or its header. After Parent: or InstanceOf:: the FHIR types and the project’s profiles, extensions and models. After from: its value sets and aliases; after insert: its rule sets; after obeys: its invariants. After * and the start of a path: the base type’s elements at that point, each with its cardinality, types and short description. After a path: the flags and rule keywords.

  • Outline: the file’s aliases, profiles, extensions, value sets, instances and the rest, in order.

These four read the text, not a finished compile, so they work while the file still has mistakes in it.

4.2 CQL and the mapping language🔗

  • Outline. A CQL library’s includes, value sets, code systems, parameters, context and definitions. A map’s imports, concept maps and groups.

  • Hover on a name shows the text of its declaration.

  • Go to definition jumps to the declaration in the file. In CQL, the name of an included library, or its alias, opens that library’s file when it is in the same folder (X.cql, X-<version>.cql, or the file whose library line names it), and C."Age" opens the definition inside it. In a map, the address after imports opens the map that declares that address, and a group it defines is found there.

  • Completion offers the names the file declares and the language’s keywords that start with what you have typed. Inside quotes, names only.

CQL’s warnings are shown as warnings. One worth knowing: comparing an Observation’s time with a period when that time may be a single moment (Checking files without an editor shows it).

5 Checking files without an editor🔗

raco fhir-lsp check runs the same check on files you name and prints the result. Use it to see what the editor should be showing, or in a script.

$ raco fhir-lsp check adults.cql

adults.cql:4:15: cql compile error: in define "Age": unknown function 'AgeInYear' (did you mean `AgeInYears` or `AgeInYearsAt`?)

 4 | define "Age": AgeInYear()

   |               ^^^^^^^^^

Each problem is one line saying where it is and what it is, then the line of the file with a marker under the place. A warning looks the same and says warning:

$ raco fhir-lsp check warn.cql

warn.cql:6:1: cql compile warning: in define "In Period": Choice<dateTime, Period, Timing, instant> against an interval reads only its Period member: a dateTime value gives null. Say which member you mean: (… as dateTime)

 6 | define "In Period": [Observation] O where O.effective during "Measurement Period"

   | ^^^^^^

You can name several files, of different languages. --format json prints the problems as JSON and --format outcome as a FHIR OperationOutcome resource, for a program to read. The command exits with 1 when any problem is an error, 0 otherwise (warnings alone are 0), and 2 when a file does not exist. A file that is not in one of the five languages is skipped with a note. A FHIR Shorthand file is checked with its project, as in the editor, so the problems of the project’s other files are listed too.

6 How it works🔗

You do not need this to use the server. It explains what to expect from it.

The server knows no language. Each language package provides one value, its support, with six functions: the problems in a text, the files that belong with it, its declarations, hover, definition and completion. The server loads a language’s support the first time a file of that language is opened, and passes requests on. So a change to a language and to what the editor shows for it are made, and tested, in the same place. A language that is not installed costs nothing and breaks nothing.

Typing is never held up. When you change a file, the server stores the new text at once, so hover and completion see it. The check itself runs on the side. If you type again before it has finished, the older result is thrown away, so you never see problems from a text you have since changed.

The project is the files around the document. For hover, definition and completion the server gathers the declarations of the files that belong with the one you are in (a FHIR Shorthand project’s .fsh files, the libraries beside a CQL library), reading open files as the editor holds them and the rest from disk.

The protocol. The server answers initialize, shutdown and exit; textDocument/didOpen, didChange, didSave and didClose; textDocument/hover, textDocument/definition, textDocument/completion and textDocument/documentSymbol; and sends textDocument/publishDiagnostics. Any other request is answered with "method not found"; other notifications are ignored. It asks the editor for the whole text on each change.

7 Limits🔗

  • FHIR Shorthand examples are compiled, not validated. The server reports what compiling the project finds. It does not hold each example to the profile it claims; raco fsh check <folder> does that, and names the rule an example breaks.

  • Hover, definition, completion and outline read the text. A name is the word under the cursor. An FHIR Shorthand element is looked up in the base type as FHIR defines it, not as a profile or a dependency has narrowed it.

  • CQL and the mapping language look beside the file. Names resolve within the file, and includes and imports reach files in the same folder. Completion of element paths is for FHIR Shorthand only.

  • VCL and FHIRPath get their problems reported and nothing else. For FHIRPath that means syntax: a misspelt element is not reported, because a file holds an expression and not the resource it is asked of.

  • No formatting, renaming or "find references".

  • A problem without a position lands on the first character of the file. A language that is not installed is reported that way.

  • Whole texts only. The server asks for the full text on every change. Every editor supports this; on a very large file it is more to send.

8 Words used here🔗

  • Language server: a program an editor runs in the background to learn about a language: its mistakes, its names, its completions.

  • Language Server Protocol (LSP): the common way editors and language servers talk, so one server works in many editors.

  • Client: the editor’s side of that conversation. Neovim has one built in; Emacs has eglot; VS Code uses an extension.

  • Diagnostic: one problem the server reports, with its place and whether it is an error or a warning.

  • Hover: what the editor shows when you rest on a name. Go to definition: jumping from a name to where it is declared. Completion: the list of what could come next. Outline (document symbols): the list of what a file declares.

  • Standard input and output (stdio): the ordinary way a program reads and writes text; here, how the editor and the server exchange messages.

  • Profile, instance: in FHIR Shorthand, a set of rules for a kind of resource, and an example resource. Parent and InstanceOf name what each is based on.

  • sushi-config.yaml: the file that states a FHIR Shorthand project’s address, FHIR version and dependencies.

9 How it is tested🔗

  • The server’s handling of each message is tested as a function from a message and a state to an answer: the handshake, opening, changing and closing a file, hover, definition, completion and outline, a message that is not JSON, shutting down.

  • Each language’s support is run on a small file with a mistake and on the corrected file: the problem must be an error naming the file (and, for FHIR Shorthand, the line), and the corrected file must come back clean.

  • What each language reports is tested in that language’s own repository, against the published test suites the family’s TESTING.md files describe.

  • The Neovim and Emacs configurations above are run in the editors themselves (tests/editors-test.rkt, with Neovim 0.10.4 and Emacs 29.3): each block is read out of this page as written and given to a headless editor, which opens the bp.fsh of step 3. The server must attach, the misspelling must be reported with the message quoted there, hover on subject must answer, and the correction must clear the problem. The test is skipped where an editor is not installed. VS Code is not tested: there is no extension of ours to run.
